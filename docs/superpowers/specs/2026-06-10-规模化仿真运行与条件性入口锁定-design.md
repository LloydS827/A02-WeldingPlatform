# 规模化仿真运行与条件性入口锁定设计

日期：2026-06-10

## 1. 背景

项目已经从“仿真入口是否能跑”推进到“可以开始组织仿真数据积累”的阶段。主线已经具备以下链路：

```text
WeldSkillUnit
-> SimulationTaskSpec
-> ManiSkill/SAPIEN batch
-> raw artifact / adapter result
-> experience dataset / SimulationEvidenceBundle
-> SimulationDatasetIndex
-> SimulationAccumulationReport
```

上一轮新增的 accumulation 启动层默认请求 2 个任务 x 50 samples，共 100 requested samples，并能输出 `accumulation_spec.json`、`dataset_index.json` 和 `accumulation_report.json`。这说明项目已经具备数据积累入口，但还没有形成 500 requested samples 级别的可复跑、可恢复、可审查运行结构。

本阶段不做最终仿真器选型，不做真实焊接质量验证，不做真实机器人执行验证。ManiSkill/SAPIEN 仍是阶段性默认积累入口，是否进入下一批默认入口，需要通过 shard 化运行、复用策略、字段覆盖和失败边界趋势来条件性判断。

## 2. 设计目标

本阶段目标是建立 **规模化仿真运行与条件性入口锁定** 的最小可行结构。

它要回答：

1. 如何把一个 accumulation run 拆成多个 batch shard。
2. 如何把默认规模从 100 requested samples 推进到 500 requested samples。
3. 如何复用已存在的 `batch_result.json`，避免每次从零重跑。
4. 如何区分新运行、复用、跳过和强制重跑。
5. 如何汇总多个 shard 的 completed / failed / skipped。
6. 如何统计 failure boundary 趋势和字段覆盖趋势。
7. 如何判断 ManiSkill/SAPIEN 是否进入 `locked_for_next_batch_with_conditions`。

本阶段仍保持最小实现：不引入数据库、队列、分布式调度、并行执行器、重型数据治理或新仿真软件。

## 3. 关键假设

- 默认任务仍沿用现有 2 个 `SimulationTaskSpec`，不新增第三个 `WeldSkillUnit`。
- 默认 Phase 2 规模为 5 shards x 100 requested samples，共 500 requested samples。
- 每个 shard 仍由现有 `run_maniskill_batch_pipeline()` 产生一个 `SimulationBatchResult`。
- 一个 shard 的 100 requested samples 由 2 个任务 x 50 samples 构成。
- shard 之间通过不同 `batch_id` 和连续 `seed_start` 区分。
- 已存在且可解析的 `batch_result.json` 默认复用。
- `--force` 表示忽略已有 `batch_result.json` 并重跑 shard。
- 复用已有 shard 不等于“跳过样本”；它是 accumulation 运行层面的 reuse 事件，样本状态仍来自原始 batch result。
- 当前 CLI 保持单进程顺序执行，后续需要时再扩展并行或外部调度。

## 4. 备选方案

### 方案 A：单 batch 直接扩大到 500 samples

做法是把现有 accumulation pipeline 的 `samples_per_task` 从 50 提升到 250，仍输出一个 batch。

优点是改动最少。缺点是失败恢复粒度太粗，无法跳过已完成 shard，也不利于比较不同 shard 的失败边界和字段覆盖趋势。一旦中途失败，下一次运行仍容易回到从零开始的状态。

### 方案 B：5 shards x 100 samples

做法是在 accumulation 层新增 shard plan，每个 shard 复用现有 batch pipeline，最终汇总为一个 dataset index 和 accumulation report。

优点是贴合当前目标：可复跑、可恢复、可审查，同时不破坏现有 batch 契约。每个 shard 的样本数保持上一轮 100 requested samples 口径，便于复用已有测试心智和 artifact 目录结构。

缺点是需要新增 shard 元数据、复用策略和汇总报告字段。

### 方案 C：引入调度系统或并行执行

做法是引入任务队列、数据库或并行 runner 来管理 shard。

优点是未来扩展性更强。缺点是明显超出当前阶段，容易把问题从“数据积累入口是否稳定”转移到“调度基础设施是否成熟”。当前没有必要。

推荐方案：**方案 B**。

## 5. 核心设计

### 5.1 Shard 计划

新增轻量 shard 计划对象，用于描述一个 accumulation run 内部的 batch shard。

建议字段：

- `shard_id`
- `batch_id`
- `samples_per_task`
- `requested_sample_count`
- `seed_start`
- `batch_root_uri`
- `batch_result_uri`
- `reuse_policy`

默认 `SimulationAccumulationBatchSpec` 增加或派生以下 scale 字段：

- `shard_count = 5`
- `samples_per_task = 50`
- `samples_per_shard = len(task_specs) * samples_per_task = 100`
- `target_requested_sample_count = 500`
- `scale_phase = "phase_2_scale_sharded_accumulation"`
- `resume_policy = "reuse_existing_batch_result_unless_force"`

为了兼容上一轮 100 requested samples 入口，现有 `default_maniskill_accumulation_spec()` 可以保留 Phase 1 默认值；新增 Phase 2 helper 或参数化入口表达 shard 默认值。实现时优先避免破坏旧测试和旧 CLI 口径。

### 5.2 恢复与复用策略

默认策略：

- 若 shard 目录下存在 `batch_result.json`，且 `--force` 未开启，则读取并通过 shard 计划一致性校验后复用。
- 若文件不存在，则运行 `run_maniskill_batch_pipeline()`。
- 若文件存在但解析失败，或与当前 shard 计划不一致，应视为 pipeline/data contract failure，不应静默复用。
- `--force` 开启时，重跑所有 shard，并覆盖对应输出。

复用前的最小一致性校验包括：

- `batch_result.batch_id` 必须等于当前 shard 的 `batch_id`。
- `batch_result.route_id` 必须等于当前 accumulation route。
- `batch_result.requested_sample_count` 必须等于当前 shard 的 `requested_sample_count`。
- `batch_result.task_count` 必须等于当前 task spec 数量。
- `sample_runs` 数量必须等于 `requested_sample_count`。
- 每条 `sample_run.batch_id` 和 `sample_run.route_id` 必须匹配当前 shard。
- 当前 shard 的 seed 范围必须与 `sample_runs` 中的 seed 集合一致。

第一版不要求读取 `batch_spec.json` 做深度结构比对；上述校验已经能防止最容易发生的旧参数产物误复用。后续如果 batch spec 演进，再把 `batch_spec.json` hash 或 spec snapshot 纳入复用校验。

建议在 accumulation report 中记录 shard 级运行状态：

- `completed_new_run`
- `reused_existing_result`
- `failed_to_load_existing_result`
- `rerun_forced`

这些状态是 shard orchestration 状态，不替代 `SimulationSampleRun.status`。

### 5.3 多 shard 汇总

现有 `build_simulation_dataset_index()` 已支持多个 `SimulationBatchResult`。本阶段应复用它，而不是重新写一个 index 体系。

需要新增或扩展的汇总信息：

- `shard_count`
- `completed_shard_count`
- `reused_shard_count`
- `failed_shard_count`
- `shard_result_uris`
- `failure_boundary_counts`
- `field_coverage_trend`

`failure_boundary_counts` 统计所有 shard 中 failure boundary 出现次数，便于判断失败边界是否集中在环境缺失、仿真运行、adapter 转换或数据契约。

`field_coverage_trend` 以 shard 为单位记录关键 URI 覆盖率，包括：

- `raw_artifact_uri`
- `adapter_result_uri`
- `experience_dataset_uri`
- `evidence_bundle_uri`
- `failure_artifact_uri`

第一版趋势只需要给出每个 shard 的覆盖率快照，不做复杂时序分析或质量评分。

### 5.4 条件性入口锁定状态

新增或扩展 accumulation 状态：

- `locked_for_next_batch_with_conditions`

触发条件建议保持保守：

- requested samples 达到 Phase 2 目标，即 500。
- 至少有 completed samples。
- 不存在 skipped samples。
- 不存在数据契约、adapter 转换、dataset 导出或 evidence 导出类失败。
- 字段覆盖在 completed samples 内稳定：completed 样本的 adapter result、experience dataset 和 evidence bundle 覆盖率均为 1.0。
- 若 failure boundary 存在，只允许环境或仿真运行类可解释失败；`environment_missing` 导致 0 completed samples 时不能锁定。
- 若存在 failed samples，每条 failed sample 必须带有非空 failure boundary，且所有 failure boundary 均属于允许集合。

状态判断优先级：

1. 若 completed = 0 且 failure boundary 包含 `environment_missing`，状态为 `blocked_by_environment`。
2. 若 completed = 0，状态为 `blocked_by_pipeline_failure`。
3. 若 completed > 0 且存在 skipped，状态为 `accumulating_with_failures`。
4. 若 completed = requested 且无 failed/skipped/failure boundaries，状态为 `ready_to_scale_with_conditions`。
5. 若 requested >= 500、completed > 0、failed > 0、completed 样本关键字段覆盖率为 1.0，且每条 failed sample 都有非空、可解释、允许的 failure boundary，状态为 `locked_for_next_batch_with_conditions`。
6. 若 completed > 0 且存在 failed，状态为 `accumulating_with_failures`。
7. 其他 completed > 0 情况为 `accumulating_completed_samples`。

这里允许 `locked_for_next_batch_with_conditions` 在存在少量可解释 failed samples 时触达，原因是真实 ManiSkill/SAPIEN 环境下规模化运行可能出现环境或仿真运行边界；但只要 completed 样本的数据契约稳定，下一批仍可以继续默认使用 ManiSkill/SAPIEN。若失败来自 `adapter_conversion_failed`、`experience_dataset_export_failed`、`evidence_export_failed` 或 `data_contract_incomplete`，说明 pipeline/data contract 本身不稳定，不能锁定。

完美 Phase 2 运行，即 500 requested samples 全部 completed 且无 failure boundaries，应继续输出 `ready_to_scale_with_conditions`。`locked_for_next_batch_with_conditions` 专门表示“存在少量可解释失败，但 completed 数据契约已经稳定，允许 ManiSkill/SAPIEN 作为下一批默认入口继续运行”。

`locked_for_next_batch_with_conditions` 不表示最终仿真器选型完成，只表示 ManiSkill/SAPIEN 可以作为下一批 accumulation 默认入口继续使用，同时仍受 stage boundary、真实焊接质量缺失和真机验证缺失约束。

### 5.5 CLI 入口

现有 CLI 保留 Phase 1 默认：

```bash
uv run python -m weldcore.simulation_bakeoff.maniskill_accumulation_pipeline \
  --outdir artifacts/simulation/maniskill-sapien-accumulations
```

新增 Phase 2 shard 入口建议为参数化方式：

```bash
uv run python -m weldcore.simulation_bakeoff.maniskill_accumulation_pipeline \
  --outdir artifacts/simulation/maniskill-sapien-accumulations \
  --accumulation-id maniskill-sapien-accumulation-phase-2 \
  --shards 5 \
  --samples-per-task 50
```

可选：

```bash
  --force
```

默认不把 Phase 1 命令改成 500 requested samples，避免破坏已有 README 和测试中的 100 requested samples 启动口径。README 应同时说明 Phase 1 启动入口与 Phase 2 shard 入口。

## 6. 输出目录

建议目录结构：

```text
artifacts/simulation/maniskill-sapien-accumulations/
└── maniskill-sapien-accumulation-phase-2/
    ├── accumulation_spec.json
    ├── dataset_index.json
    ├── accumulation_report.json
    └── batches/
        ├── maniskill-sapien-accumulation-phase-2-shard-000/
        │   ├── batch_spec.json
        │   ├── batch_result.json
        │   └── samples/
        ├── maniskill-sapien-accumulation-phase-2-shard-001/
        └── ...
```

`dataset_index.json` 中的 item URI 继续保持相对 batch root。完整文件定位由 `batch_root_uris[batch_id] + item.uri` 组合得到。

## 7. 测试策略

新增或扩展测试应覆盖：

- Phase 1 默认仍为 100 requested samples。
- Phase 2 shard spec 默认为 5 shards x 100 = 500 requested samples。
- shard seed_start 连续且不重叠。
- 已存在 `batch_result.json` 时默认复用，不调用 batch runner。
- `--force` 时重跑 shard。
- 多 shard dataset index 汇总 requested / completed / failed / skipped。
- failure boundary counts 可反映跨 shard 趋势。
- completed sample 字段覆盖为 1.0 时可进入 `locked_for_next_batch_with_conditions`。
- 环境缺失导致 0 completed samples 时仍为 `blocked_by_environment`，不能锁定。
- CLI 可输出 500 requested samples 报告。

验证命令：

```bash
cd weld-experience-engine
uv run pytest tests/test_simulation_accumulation_models.py tests/test_maniskill_accumulation_pipeline.py -q
uv run pytest -q
```

需要同步更新：

文档口径：

- Phase 1：100 requested samples accumulation 启动入口仍保留。

- `locked_for_next_batch_with_conditions` 只是条件性继续使用 ManiSkill/SAPIEN 的入口判断，不是最终仿真器选型。
- 缺少 ManiSkill/SAPIEN 环境时，blocked 状态是环境边界，不是否定 pipeline。

## 9. 不做事项

- 不新增第三个默认 `WeldSkillUnit`。
- 不切换到 Gazebo/MoveIt 或 Isaac 作为默认实现。
- 不引入真实机器人控制、ROS 执行、碰撞检测或关节限制验证。
- 不把仿真数据写成真实焊接质量结论。
- 不引入数据库、队列、并行调度或 UI。
- 不做字段级数据治理评分，只做 shard 级覆盖趋势。

## 10. 成功标准

本阶段完成后，应满足：

- 默认 Phase 1 入口保持兼容。
- Phase 2 可通过 CLI 请求 5 shards x 100 = 500 samples。
- 已完成 shard 可被复用，`--force` 可显式重跑。
- accumulation report 汇总 shard 级运行状态、failure boundary 趋势和字段覆盖趋势。
- 满足条件时输出 `locked_for_next_batch_with_conditions`。
- 文档明确当前仍不代表最终仿真器选型、真实焊接质量验证或真实机器人执行验证。
- 全量测试通过。
