# 仿真输出接入与焊接经验沉淀平台 — 设计 Spec

日期：2026-06-03
版本：v0.1
适用项目：A02 焊接技能大师平台
阶段：`SyntheticSkillDataset v2` 输入规范 gate 通过后，进入真正仿真工作前

---

## 0. 结论先行

下一阶段不应先押注某一个仿真器，也不应直接大范围重写平台。应采用 **仿真输出接入为主线、系统收束为辅线** 的方案：

```text
SimulationInputSpec
-> 外部仿真器执行
-> SimulationOutputBundle
-> 平台导入与 gate
-> SyntheticSkillDataset v2
-> WeldSkillPackage
-> TransferExperiment
-> EvidenceReport
```

本阶段的核心目标是让平台具备第一项真正面向仿真的能力：**接收仿真输出，并把仿真输出沉淀为可追溯、可审计、可复用的焊接经验数据资产**。

ManiSkill、Isaac Sim、Isaac Lab、SAPIEN 或其他开源仿真生态都作为外部执行器或后续 adapter 候选。平台核心不能依赖某个仿真器的私有输出格式，而应先定义自己的 canonical input/output schema。后续生态选型必须回答一个更基础的问题：它是否能输出或转换为平台要求的 `SimulationOutputBundle`。

同时，本阶段要收束前期 POC、MVP、资料底座、输入规范和报告中的路线表达。前期调研资料不能删除，它们仍是后续焊接知识嵌入、工艺知识组织、证据追溯和专家审查的知识底座；收束的目标是把它们放回正确位置，而不是把有用资料清空。

---

## 1. 已确认关键决策

1. 项目总目标仍然是把高级焊工/焊接大师技能迁移到机器人，并通过平台沉淀为可复用的技能资产。
2. 当前主路线是仿真优先。真机、专家访谈、WPS/PQR、检测结果和船级审查保留为后续校准、验证和审查环节。
3. 下一阶段先做平台 I/O 能力，而不是先选定单一仿真生态。
4. 平台第一核心能力是接住仿真输出，保存其中代表经验的数据结构，再支撑后续技能包提取、迁移、评测和知识嵌入。
5. ManiSkill 是第一批开源仿真生态候选；Isaac 系列可作为后续高保真、机器人数字孪生和工业场景方向；核心数据模型不直接依赖二者。
6. 前期调研资料、公开数据集 manifest、字段覆盖矩阵、任务证据映射和 input-spec gate 继续保留，并作为后续知识嵌入来源。
7. 本阶段要做必要的系统收束和重构，但只围绕仿真接入、经验沉淀和证据闭环展开。
8. 不做完整业务平台 UI，不做生产数据库，不做真实机器人控制，不做 WPS/PQR，不做熔池闭环。

## 2. 背景与当前系统自查

项目已经完成五条证据链：

- 经验结构化 POC：验证轨迹可以被拆解为结构化工艺参数并重组。
- 技能迁移 MVP：验证仿真样本可以进入 `SkillDataset`，生成 `WeldSkillPackage`，完成迁移评测和报告。
- 仿真优先知识闸门：从公开资料和船舶制造任务族生成候选 `SimulationScenarioSpec`。
- 资料底座 gate：用 manifest 记录资料来源、公开数据集、字段覆盖和任务证据映射。
- `SyntheticSkillDataset v2` 输入规范 gate：定义任务分类、工艺字段、仿真输入、证据绑定和真实验证边界。

这些成果说明：平台已有机制雏形，但还没有真正接入外部仿真输出。

### 2.1 已有能力

现有代码已经具备以下基础对象：

| 能力 | 当前对象 | 可继续使用的原因 |
| --- | --- | --- |
| 轨迹保存 | `Trajectory` / `TrajectorySample` | 已能保存 TCP 时间序列、位置、姿态、电流、电压和力占位 |
| 过程信号 | `ProcessSignal` | 已能保存电流、电压、送丝、行走速度 |
| 样本容器 | `SkillSample` | 已能把焊接条件、轨迹、过程信号、事件、质量观察和 artifact 放在一起 |
| 数据集容器 | `SkillDataset` | 已能标注 `source_type = simulation` 并保存多个样本 |
| 经验提取 | `package_from_sample` / `WeldSkillPackage` | 已能从样本提取运动、姿态和过程技能雏形 |
| 迁移评测 | `TransferExperiment` | 已能记录迁移条件、评测指标和 pass/review/fail |
| 证据绑定 | `EvidenceBinding` | 已能区分公开来源、仿真假设、仿真输出和后续真实验证 |
| 输入规范 gate | `SyntheticInputFoundation.validate()` | 已能校验 ready 任务、字段绑定、质量边界和禁止字段 |
| 报告链路 | `mvp_report` / `scenario_report` / `data_foundation_report` / `synthetic_v2_input_report` | 已有可复现报告输出模式 |

### 2.2 当前缺口

当前系统仍缺少仿真接入所需的关键能力：

- 没有外部仿真输出的统一包格式。
- 没有仿真结果上传/导入协议。
- 没有 `SimulationRunRecord` 记录一次仿真的输入、执行器、版本、seed、输出、状态和错误。
- 没有 adapter 把 ManiSkill/Isaac/其他仿真器输出转换为平台 canonical schema。
- 没有批量 `SyntheticSkillDataset v2` 样本 manifest。
- `WeldCondition` 仍偏 MVP，无法完整表达船舶任务族、坡口、层道、多短焊缝和证据状态。
- 平台目前能在代码内保存样本，但还不是“上传、校验、归档、审计、报告”的流程能力。
- 文档中仍有 POC、MVP、真机、平台化、资料 gate、input-spec gate 等多阶段表达，需要重新收束到仿真主线。

## 3. 范围边界

### 3.1 本阶段做什么

- 定义仿真输出统一接口 `SimulationOutputBundle`。
- 定义一次仿真运行记录 `SimulationRunRecord`。
- 定义从仿真 bundle 到 `SkillDataset` / `SyntheticSkillDataset v2` 的导入 adapter 边界。
- 扩展或补充能承接船舶焊接仿真输出的数据结构。
- 建立仿真输出 gate，校验字段、来源、假设、真实验证边界、禁止字段和 artifact 完整性。
- 生成仿真接入证据报告，说明导入了哪些样本、来自哪个 input spec、由哪个仿真器产生、哪些字段是假设或待验证。
- 使用 mock/轻量仿真输出证明平台能接住数据；真实 ManiSkill/Isaac 接入可在下一实施阶段从 adapter 边界开始。
- 收束 README、`details.md`、相关 spec/plan 和报告中的阶段表述。
- 对工程代码做必要模块边界整理，围绕 `model`、`sim`、`knowledge`、`report` 和未来 `io`/`ingest` 能力展开。

### 3.2 本阶段不做什么

- 不实现完整 ManiSkill 或 Isaac 仿真任务环境。
- 不把某个仿真器设为平台基础依赖。
- 不生成大规模 synthetic 数据集。
- 不做生产级数据库、权限系统或完整平台 UI。
- 不实现真实机器人控制、焊机控制、现场采集或 MES/PLM/QMS 接口。
- 不做 WPS/PQR、真实焊接质量合格声明、船级审查结论。
- 不纳入熔池图像、熔池控制或焊中闭环路线。
- 不删除前期调研资料；只调整其在路线中的位置和引用方式。

## 4. 方案取舍

### 4.1 方案 A：先做仿真生态选型

做法：先比较 ManiSkill、Isaac Sim、Isaac Lab、SAPIEN、MuJoCo、ROS 2/MoveIt/Gazebo，再确定实现路线。

优点：

- 容易形成工具路线。
- 有助于后续算力、环境和技术栈准备。

问题：

- 容易让平台被某个仿真器的输出格式牵着走。
- 还没有定义平台要接收什么数据，选型标准会漂。
- 无法回答“仿真结果如何成为焊接经验资产”这个核心问题。

结论：不作为第一步。

### 4.2 方案 B：先重构整个系统

做法：全面整理文档、代码、模块、命名和报告，再进入仿真。

优点：

- 长期会更整洁。
- 可以消除前期绕路留下的混乱。

问题：

- 容易变成大范围翻修，推迟真正仿真工作。
- 很多重构没有仿真接入的真实需求约束，容易过度设计。

结论：不采用大重构，只做围绕主线的必要收束。

### 4.3 方案 C：仿真输出接入为主线，系统收束为辅线

做法：先定义平台 canonical I/O 和经验沉淀流程，再围绕这条主线整理文档和代码边界。

优点：

- 直接服务下一步真正仿真工作。
- 能保留前期调研资料价值，同时清理阶段表达。
- 可以把 ManiSkill/Isaac 等生态纳入 adapter 对比，而不是绑定核心模型。
- 有明确验收：平台能导入一个仿真输出 bundle 并生成 `SkillDataset` 和报告。

问题：

- 需要严格控制收束范围，避免变成全项目重构。

结论：**推荐采用。**

## 5. Canonical I/O 设计

### 5.1 输入侧：`SimulationInputSpec`

现有 `SimulationInputSpec` 继续作为仿真前输入规范。它定义：

- `input_id`
- `taxonomy_ref`
- `procedure_fields`
- `geometry_spec`
- `motion_spec`
- `process_spec`
- `quality_spec`
- `variant_policy`
- `evidence_bindings`
- `generation_boundary`

后续仿真器不得直接绕过该输入规范生成样本。第一版 `SimulationOutputBundle` 采用 **单 input、多 sample** 约束：每个 bundle 只对应一个 `SimulationInputSpec.input_id`，但可以包含该 input 下的多个样本。跨多个 input 的批量生成由多个 bundle 和同一个或多个 `SimulationRunRecord` 组织，不在单个 bundle 内混放。

### 5.2 输出侧：`SimulationOutputBundle`

新增统一输出包格式，用于承接任何仿真器输出。建议目录结构：

```text
simulation_output_bundle/
├── manifest.json
├── trajectory.csv
├── process_signals.csv
├── events.json
├── quality_placeholders.json
├── evidence_bindings.json
└── artifacts/
    ├── recording.rrd
    ├── scene.usd
    ├── simulator_log.txt
    └── preview.png
```

第一版不要求所有 artifact 都存在，但 `manifest.json`、`trajectory.csv`、`process_signals.csv` 和 `evidence_bindings.json` 必须存在并可校验。若某些过程信号值不可用，应在 `process_signals.csv` 中保留 canonical 列并使用空值，同时在 `manifest.json` 的缺失说明中记录原因，不允许省略 `process_signals.csv`。

### 5.3 `manifest.json`

`manifest.json` 记录一次仿真输出的索引信息：

| 字段 | 说明 |
| --- | --- |
| `bundle_id` | 输出包编号 |
| `simulation_run_id` | 仿真运行编号 |
| `input_id` | 对应 `SimulationInputSpec.input_id` |
| `taxonomy_ref` | 对应任务族 |
| `simulator` | `simlite` / `maniskill` / `isaac_sim` / `isaac_lab` / `sapien` / `other` |
| `simulator_version` | 仿真器版本或 unknown |
| `adapter_version` | 平台 adapter 版本 |
| `seed` | 随机种子 |
| `sample_count` | 样本数量 |
| `generated_at` | 生成时间 |
| `source_type` | 必须为 `simulation` |
| `schema_version` | 固定为 `synthetic-v2-bundle-v0.1` |
| `assumption_summary` | 关键仿真假设摘要 |
| `requires_real_validation_later` | 是否包含待真实验证字段 |
| `missing_signal_notes` | 过程信号缺失说明；无缺失时为空列表 |
| `generation_boundary` | 边界声明 |

### 5.4 轨迹与过程信号

`trajectory.csv` 第一版字段：

```text
sample_id,t,x,y,z,rx,ry,rz,current,voltage,force
```

`process_signals.csv` 第一版字段：

```text
sample_id,t,current,voltage,wire_feed,travel_speed
```

字段单位沿用现有模型：

- 时间：s
- 位置：mm
- 姿态：deg
- 电流：A
- 电压：V
- 力：N
- 行走速度：mm/s

如果外部仿真器使用 m、rad、关节角或四元数，adapter 必须转换为平台 canonical 单位和姿态表达，并在 `SimulationRunRecord` 中记录转换说明。

### 5.5 事件和质量占位

`events.json` 记录仿真过程事件，例如：

- `arc_start`
- `arc_end`
- `segment_start`
- `segment_end`
- `reposition`
- `collision_warning`
- `reachability_warning`
- `adapter_warning`

`quality_placeholders.json` 只能记录仿真评分、公开标签词汇或待验证占位，例如：

- `geometry_risk_label`
- `defect_vocabulary_placeholder`
- `simulation_score_placeholder`
- `requires_real_validation_later`

不得写成真实焊接质量合格结论。

## 6. 经验沉淀数据结构

### 6.1 `SyntheticSkillDataset v2`

第一版不另造完全独立格式，而是在现有 `SkillDataset` 上扩展：

- `schema_version` 固定为 `synthetic-v2-dataset-v0.1`。
- `source_type` 必须为 `simulation`。
- `task` 使用 `taxonomy_ref` 或更可读的任务名。
- `license_and_rights` 标注为内部生成 synthetic 数据或具体来源边界。
- `recording_artifact` 指向 bundle 中的 artifact。
- 样本必须保留 `input_id`、`simulation_run_id` 和 evidence 追溯信息。

### 6.2 `SkillSample` 扩展方向

现有 `SkillSample` 需要补充或通过 metadata 承接：

| 字段 | 作用 |
| --- | --- |
| `input_id` | 对应仿真输入规范 |
| `simulation_run_id` | 对应一次仿真运行 |
| `taxonomy_ref` | 对应船舶任务族 |
| `evidence_bindings` | 样本级证据绑定 |
| `assumptions` | 样本级仿真假设 |
| `artifact_refs` | 轨迹、日志、场景、可视化、回放文件 |
| `validation_status` | `synthetic_only` / `requires_real_validation_later` |

具体实现可以选择新增 dataclass，也可以先通过 `metadata` 字段承接；实施计划阶段再根据代码复杂度选择。

### 6.3 `WeldCondition` 扩展方向

当前 `WeldCondition` 只有 MVP 所需字段。为承接船舶仿真任务，第一版需要至少能表达：

- `weld_type`
- `joint_type`
- `plate_thickness_mm`
- `groove_width_mm`
- `length_mm`
- `position`
- `material`
- `manufacturing_stage`
- `weld_object`
- `groove_geometry`
- `layer_pass`
- `access_context`
- `motion_structure`

不要求第一版做完整 WPS/PQR，也不要求所有字段都有真实数值。缺失或假设字段必须保留证据状态。

## 7. 仿真运行记录

新增 `SimulationRunRecord`，用于记录一次仿真执行：

| 字段 | 说明 |
| --- | --- |
| `simulation_run_id` | 运行编号 |
| `input_ids` | 本次运行使用的输入规范；一次 run 可以生成多个 bundle |
| `simulator` | 仿真器名称 |
| `simulator_version` | 仿真器版本 |
| `adapter_name` | adapter 名称 |
| `adapter_version` | adapter 版本 |
| `seed` | 随机种子 |
| `started_at` / `finished_at` | 运行时间 |
| `status` | `created` / `running` / `completed` / `failed` / `imported` |
| `output_bundle_uris` | 输出包路径列表；第一版通常一个 run 对应一个 bundle，但允许同一 run 记录多个 bundle |
| `sample_count` | 样本数量 |
| `warnings` | 导入或仿真警告 |
| `errors` | 错误信息 |
| `boundary_notes` | 真实验证、WPS/PQR、质量结论边界 |

该对象用于把“仿真跑过一次”变成平台可追踪事实，而不是只留下散落文件。

## 8. Adapter 策略

### 8.1 统一边界

每个仿真生态只需要实现两件事：

```text
SimulationInputSpec -> simulator-native input
simulator-native output -> SimulationOutputBundle
```

平台内部只消费 `SimulationOutputBundle`，不直接消费仿真器私有对象。

### 8.2 ManiSkill

ManiSkill 作为第一候选开源生态边界，适合评估：

- 机器人任务环境组织。
- demonstration 数据和 replay 习惯。
- GPU 并行采样和任务构建方式。
- 与 `Trajectory`、`ProcessSignal`、`SkillDataset` 的转换关系。

第一版不把 `mani_skill` 设为基础依赖。实现上可以保留 optional adapter 或 mock adapter。

### 8.3 Isaac 系列

Isaac Sim / Isaac Lab 作为后续增强方向，适合评估：

- 高保真场景。
- 机器人数字孪生。
- 传感器 synthetic data。
- ROS 2 接入。
- 强化学习或模仿学习。

第一版只定义 adapter 预留口径，不强制安装或运行。

### 8.4 `simlite`

现有 `simlite` 继续作为平台内部测试执行器，用于：

- 快速生成 mock bundle。
- 验证导入 gate。
- 验证报告和 `SkillDataset` 转换。
- 在没有外部仿真环境时保持测试稳定。

## 9. 平台流程支撑

第一版平台流程是研发工作台能力，不是完整业务 UI：

```text
1. 选择 ready SimulationInputSpec
2. 创建 SimulationRunRecord
3. 外部仿真器或 simlite 生成 SimulationOutputBundle
4. 平台导入 bundle
5. 校验字段、单位、证据绑定、质量边界和禁止字段
6. 转换为 SyntheticSkillDataset v2
7. 生成导入证据报告
8. 可选提取 WeldSkillPackage
9. 可选运行 TransferExperiment
```

### 9.1 导入 gate

导入 gate 至少校验：

- `input_id` 存在并来自 ready 任务。
- `taxonomy_ref` 与 input spec 一致。
- `source_type = simulation`。
- 轨迹字段完整。
- `process_signals.csv` 存在，canonical 列完整；允许值为空，但必须在 `missing_signal_notes` 中说明。
- 单位转换已记录。
- 每个关键字段有 `EvidenceBinding` 或继承自 input spec。
- 质量相关字段包含 `requires_real_validation_later` 或 `simulation_score_placeholder`。
- bundle 中不得包含当前阶段禁止字段：`熔池`、`molten_pool`、`weld_pool` 等。
- artifact 路径存在或有明确缺失说明。

### 9.2 导入报告

新增导入报告应输出：

- run summary。
- bundle summary。
- sample summary。
- input spec 对齐结果。
- evidence binding 摘要。
- assumption fields。
- real-validation fields。
- warnings/errors。
- 后续能否进入 skill package 提取。

## 10. 前期调研资料的保留与后续知识嵌入

前期调研资料是后续知识嵌入的基础，不应删除。它们在新阶段中的位置如下：

| 资料 | 新阶段用途 |
| --- | --- |
| `sources.json` | 作为来源索引和证据绑定来源池 |
| `datasets.json` | 作为公开数据集 schema、标签和 benchmark 参考 |
| `field_coverage.csv` | 作为字段来源、仿真假设和验证状态的映射基础 |
| `task_evidence_map.json` | 作为 ready 任务选择依据 |
| `synthetic_v2_input_research.md` | 作为焊接任务、工艺字段、质量词汇和仿真边界调研总结 |
| `synthetic_v2_field_gap_matrix.csv` | 作为后续知识嵌入和字段补齐的 gap 清单 |

后续完成仿真接入后，下一步知识嵌入可以围绕这些资料开展：

```text
公开资料/标准入口/数据集 schema
-> 焊接知识条目
-> 字段/任务/质量词汇绑定
-> 专家审查
-> 技能包适用条件和迁移规则增强
```

本阶段只保留这个接口，不实现完整知识图谱、RAG 或专家系统。

## 11. 系统收束与必要重构

### 11.1 文档收束

需要统一以下表述：

- 当前阶段是进入真正仿真前的输出接入与经验沉淀平台设计。
- POC/MVP 是机制证明，不是最终平台。
- 资料底座和 input-spec gate 是仿真前置知识与输入规范，不是批量数据生成。
- 仿真输出接入完成后，才进入外部生态仿真执行和小批量数据生成。
- 真机、WPS/PQR、专家访谈、质量检测是后续验证与审查，不是当前主路径。
- 前期调研资料继续保留，后续用于焊接知识嵌入。

优先检查：

- `README.md`
- `details.md`
- `weld-experience-engine/README.md`
- `docs/data-foundation/README.md`
- 相关 superpowers specs/plans 的阶段说明

### 11.2 代码收束

代码收束围绕以下边界：

| 模块 | 收束方向 |
| --- | --- |
| `weldcore.model` | 保持核心数据结构与仿真器无关 |
| `weldcore.knowledge` | 继续负责资料、input spec 和 evidence gate |
| `weldcore.sim` | 保留 `simlite`，新增或整理 adapter 边界 |
| `weldcore.report` | 新增仿真导入证据报告 |
| `weldcore.transfer` | 继续从 `SkillDataset`/`SkillSample` 提取技能包 |
| 新增 `weldcore.ingest` 或 `weldcore.io` | 承接 bundle 导入、schema 校验和转换 |

不做无关重构，不因为命名不完美而重写旧模块。每个改动必须能追溯到仿真输出接入、经验沉淀或阶段收束。

## 14. 验收标准

本阶段完成时应满足：

1. 写明并实现 `SimulationOutputBundle` 第一版 schema。
2. 写明并实现 `SimulationRunRecord` 第一版数据结构。
3. 至少支持从一个 mock/simlite bundle 导入为 `SkillDataset`。
4. 导入结果保留 `input_id`、`taxonomy_ref`、`simulation_run_id`、artifact、assumption 和 evidence 信息。
5. 导入 gate 能拒绝缺少关键字段、质量边界缺失、未知 input id、非 ready 任务和禁止字段。
6. 生成仿真导入证据报告。
7. 最低验收覆盖至少一个 ready 任务的端到端导入测试；推荐三个 ready 任务都拥有 mock bundle fixture 或生成路径。
8. 被覆盖任务的导入测试必须验证 bundle schema、gate、`SkillDataset` 转换和证据报告。
9. 现有 108 个测试继续通过。
10. README、`details.md` 和子项目 README 的阶段表述更新为当前路线。
11. 前期调研资料保留，并在新文档中说明其后续知识嵌入用途。
12. 不引入 ManiSkill 或 Isaac 作为基础运行依赖。
13. 不生成真实质量验证、WPS/PQR 或熔池闭环相关结论。

## 15. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 过早绑定仿真生态 | 先定义 bundle 和 adapter，核心模型只消费 canonical schema |
| 系统收束变成大重构 | 每个改动必须服务仿真接入或经验沉淀 |
| 删除有用调研资料 | 明确调研资料是后续知识嵌入底座，只收束表述，不删除资料 |
| synthetic 数据被误写成真实质量 | gate 和报告强制保留 `requires_real_validation_later` |
| ManiSkill/Isaac 环境复杂导致测试不稳定 | 第一版使用 mock/simlite，外部生态保持 optional adapter |
| `SkillDataset` 扩展过度 | 先用最小字段和 metadata 承接，实施阶段再根据测试需求细化 |
| 多短焊缝任务复杂度过高 | 第一版用 segment metadata 和事件表达，不实现完整复杂路径规划 |

## 16. 当前设计自审

本 spec 聚焦一个可实施目标：让平台接住仿真输出并沉淀经验。它没有把下一阶段扩大成完整仿真器开发、完整平台 UI 或真实焊接验证。

前期资料底座、公开数据集、字段矩阵和 input-spec gate 被保留为知识来源，而不是被视为旧路线包袱。系统收束也只围绕主线进行：文档要解释清楚阶段关系，代码要形成导入、校验、归档、报告和技能提取的边界。

因此，后续 implementation plan 应优先从最小可验证闭环开始：

```text
定义 bundle schema
-> 写 gate 测试
-> 写 mock/simlite bundle
-> 导入 SkillDataset
-> 输出报告
-> 更新文档
```
