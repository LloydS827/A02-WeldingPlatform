# Physical AI 焊接技能资产项目级重构 — 设计 Spec

日期：2026-06-04
版本：v0.1
适用项目：A02 焊接技能大师平台
阶段：基础功能与数据结构初步成立后，进入仿真路线与场景选择前

---

## 0. 结论先行

本项目第一阶段应先做 **技能资产主线型项目级重构**，再进入下一阶段的类机器人仿真与焊缝技能单元推进。

重构后的项目不应继续表现为 POC、报告、资料 gate、input-spec gate、simulation-ingest gate 的堆叠集合，而应表现为一个围绕 `WeldSkillPackage` 展开的 Physical AI 焊接技能资产研发底座：

```text
工艺知识 / 动作经验 / 过程数据
-> SkillDataset
-> WeldSkillPackage
-> 机器人训练 / 类机器人仿真 / 执行基线
-> 评测、证据、边界
```

其中，`WeldSkillPackage` 是项目的核心对象；仿真器、机器人、焊机、工作站、报告和资料系统都是服务技能资产沉淀、迁移、执行和审计的组件。

本阶段重构的目标不是删除前期成果，而是重新归位：前期 POC、MVP、资料底座、输入规范 gate 和仿真输出接入 gate 都保留为历史证据、技术原型或边界机制，不再作为项目默认主线本身。

## 1. 战略依据

本 spec 以 `docs/strategy/2026-06-04-PhysicalAI公司顶层战略与方向.docx` 为主要依据。该文档给出的核心判断是：

1. 公司方向是面向高技能工业作业的 Physical AI 技能系统。
2. 焊接是第一场景，但不是孤立小应用；它用于验证高技能工业作业能否被资产化。
3. 核心对象不是模型、仿真器或机器人程序，而是工业技能资产。
4. 焊接场景中的核心资产可称为 `WeldSkillPackage`。
5. `WeldSkillPackage` 至少应包含任务、来源、轨迹、姿态、工艺参数、适用范围、迁移规则、失败边界、机器人执行建议和证据状态。
6. 机器人是执行身体，数据和证据是记忆，技能资产是核心。
7. 仿真器、大模型、可视化工具和外部机器人生态都是组件，不能替代项目核心。
8. 当前不承诺仿真结果等于真实焊接质量，不自动生成或替代 WPS/PQR，不把熔池视觉闭环或焊中闭环控制作为当前起点。

因此，项目级重构必须让仓库结构、文档入口、代码边界和后续计划都服务同一个判断：

> 每一次研发动作是否让焊接技能更接近成为可复用、可迁移、可执行、可审计的工业技能资产。

## 2. 已确认决策

1. 第一阶段先做项目级重构，第二阶段再围绕主线推进仿真与场景。
2. 第一阶段允许移动、改名、归档和重排项目内所有内容。
3. 重构采用“技能资产主线型”方案，不采用轻量入口重排，也不推倒重建。
4. 默认主线以 `WeldSkillPackage` / 工业技能资产为中心。
5. 机器人训练、类机器人仿真、执行评测和质量证据是围绕技能资产的支撑链路。
6. 场景选择不应过早绑定船舶构件，例如只绑定 `stiffened-panel-fillet`；应上移到焊缝情况、焊接姿态和动作技能单元。
7. 用户当前接触的实际验证方向包括类似中组立/现场构件焊接语境下的 U 型缝、包角、长直焊缝、横焊、立焊等任务。具体术语应在后续资料调研阶段校正。
8. 仿真方式应偏类机器人仿真，因为最终目标是把技能经验变成数据结构，并服务机器人执行与机器人大脑训练。
9. 旧成果不能因为重构被误删；应归档、索引、降级为历史证据或支撑机制。
10. 重构后默认项目状态必须可安装、可运行、可验证。

## 3. 当前问题

当前仓库已经完成多条可运行证据链，但结构上存在三个问题。

### 3.1 默认主线偏阶段产物

README 和文档体系主要围绕 POC、MVP、资料底座 gate、input-spec gate 和 simulation-ingest gate 展开。它准确记录了前期工作，但打开项目时，读者首先看到的是阶段性产物，而不是项目要长期建设的核心系统。

这会导致后续研发继续围绕“下一个 gate”或“下一个报告”推进，而不是围绕 `WeldSkillPackage` 是否更可学习、可迁移、可执行、可审计推进。

### 3.2 场景抽象层级偏低

前一轮路线已经把下一阶段收束到 `stiffened-panel-fillet`。这对船舶制造资料 gate 是合理的，但对当前业务判断来说仍然偏具体构件。

用户当前更关心的是焊缝情况和操作姿态，例如 U 型缝、包角、长直焊缝、横焊、立焊。这些更接近技能资产的可迁移单元：同一种焊缝技能可以出现在不同构件、不同客户、不同机器人系统中。

### 3.3 仿真路线仍未从技能资产倒推

当前项目已经有 simlite/mock bundle 和 simulation ingest gate，但它更像平台 I/O 能力验证。下一步真正需要判断的是：什么样的类机器人仿真最能服务技能资产沉淀、机器人执行和机器人大脑训练。

仿真路线不应从某个仿真器出发，而应从 `WeldSkillPackage` 需要哪些训练数据、动作约束、执行评测和证据边界出发。

## 4. 第一阶段范围

### 4.1 本阶段做什么

第一阶段做项目级重构设计与实施准备，后续 implementation plan 再执行文件移动和文档修改。

本阶段设计覆盖：

- 设计目标目录结构。
- 设计旧成果归档规则。
- 设计核心文档入口。

- 设计 `WeldSkillPackage` 为中心的数据流。
- 设计第二阶段仿真路线的承接方式。
- 设计验收标准与验证命令。

### 4.2 本阶段不做什么

- 不直接选择唯一仿真生态。
- 不生成新的大规模数据集。
- 不把 U 型缝、包角、横焊或立焊直接写成真实质量结论。
- 不声称仿真结果等于真实焊接质量。
- 不生成或替代 WPS/PQR。
- 不把熔池视觉、熔池控制或焊中闭环作为当前起点。
- 不把前期 POC、MVP、资料 gate 或报告删除。

## 6. 文档重构规则

### 6.1 根目录 README

根目录 README 应从“已完成六条证据链”改为“Physical AI 焊接技能资产底座”。

默认 README 应优先回答：

1. 项目目标是什么。
2. 核心对象是什么。
3. 当前已经具备哪些基础能力。
4. 下一阶段为什么要先重构，再进入类机器人仿真。
5. 如何运行最小验证。
6. 哪些内容是历史证据，在哪里查。

README 不应继续把 `stiffened-panel-fillet` 写成唯一默认主线；它可以作为历史候选或资料 gate 结论之一，但新的默认主线应上移到焊缝技能单元。

### 6.2 details.md

`details.md` 继续作为面向非技术读者的进展台账，但阶段判断需要更新为：

```text
项目已经完成基础功能和数据结构的第一轮验证。
当前进入第一阶段项目级重构：把前期 POC/gate/报告成果重新归位，
围绕 WeldSkillPackage 建立默认主线。
重构完成后，再进入焊缝技能单元与类机器人仿真路线。
```

同时应明确：

- 已完成的是基础机制，不是真实质量验证。
- 当前重点不是继续堆报告，而是把系统主线整理清楚。
- 旧资料仍保留，但默认叙事需要服务技能资产。

### 6.3 docs/architecture

新增或迁移架构文档，用于承接战略文档中的五层系统：

```text
工艺知识层
技能数据层
技能资产层
机器人执行层
证据与边界层
```

架构文档应明确每一层的职责、输入、输出、依赖和不做事项。

### 6.4 docs/skill-assets

新增技能资产文档入口，作为后续研发主线。

第一版至少包含：

- `WeldSkillPackage` 的字段定义。
- `SkillDataset` 与 `WeldSkillPackage` 的关系。
- 焊缝技能单元的分类框架。
- 迁移边界和失败边界。
- 机器人执行建议如何进入技能包。
- 证据状态如何绑定到技能包。

### 6.5 docs/simulation

新增仿真路线入口。第一版应说明：

- 当前仿真主线是类机器人仿真，不是熔池物理仿真。
- 仿真的第一价值是验证技能资产能否成为机器人可执行、可评测、可训练的数据结构。
- 仿真器只是 adapter 候选。
- simlite 是稳定测试工具，不是最终仿真路线。
- ManiSkill、SAPIEN、Isaac、ROS/MoveIt/Gazebo 等都应按 adapter 方式评估。

### 6.6 docs/evidence

把资料底座、source cards、字段覆盖、证据报告、质量边界集中到 evidence 体系下。

资料不再作为“路线主线”出现，而是作为：

- 工艺知识来源。
- 字段来源。
- 任务和技能单元约束。
- 证据边界。
- 不能做真实质量结论的限制说明。

### 6.7 docs/archive

前期 POC、MVP、旧 superpowers spec/plan、白皮书和旧报告进入 archive 或保留原路径但建立 archive index。

归档规则：

- 能证明历史路线和技术能力的材料不删除。
- 默认 README 不把归档内容作为主线入口。
- 归档文档要有索引，说明其用途、阶段、是否仍可运行。
- 归档不是失败，而是把阶段性成果放回正确上下文。

## 7. 代码边界设计

第一阶段不建议大规模改包名，因为当前测试和报告命令已经可运行。代码重构应遵循“先主线解释清楚，再逐步调整边界”的原则。

### 7.1 当前代码可保留的核心

当前 `weld-experience-engine/weldcore` 中以下能力仍服务主线：

- `model/skill.py`：`SkillDataset`、`SkillSample`、`WeldSkillPackage` 等核心对象。
- `transfer/`：技能迁移与评测规则。
- `sim/`：轻量仿真和 mock bundle，作为稳定测试工具。
- `ingest/`：仿真输出接入边界。
- `knowledge/`：资料、任务和字段约束。
- `report/`：证据输出。
- `viz/`：可选回放和调试边界。

### 7.2 后续代码目标边界

后续 implementation plan 可逐步引入或整理这些边界：

```text
weldcore/
├── model/          # 通用数据模型，保留向后兼容
├── skill_asset/    # 以 WeldSkillPackage 为中心的资产构建、版本、边界
├── skill_data/     # SkillDataset、样本来源、时间轴和字段绑定
├── knowledge/      # 工艺知识、资料、术语、字段来源
├── simulation/     # 类机器人仿真抽象与 adapter
├── robotics/       # 机器人执行建议、可达性、轨迹基线
├── evidence/       # 证据、报告、质量边界、审计
└── archive/        # 若需要保留旧 POC 代码，可通过文档归档，不优先建代码 archive
```

第一轮实施不必一次性创建所有包。可以先通过文档、README 和少量 facade 模块完成主线收束，避免破坏 `uv run pytest -q`。

### 7.3 默认命令边界

重构后默认命令应从“生成多个阶段报告”收束为：

```bash
cd weld-experience-engine
uv run pytest -q
```

报告命令仍保留，但作为历史证据或辅助验证：

```bash
uv run python -m weldcore.report.generate
uv run python -m weldcore.report.mvp_report
uv run python -m weldcore.report.scenario_report
uv run python -m weldcore.report.data_foundation_report
uv run python -m weldcore.report.synthetic_v2_input_report
uv run python -m weldcore.report.simulation_ingest_report
```

后续应新增一个更贴合主线的报告命令，例如：

```bash
uv run python -m weldcore.report.skill_asset_report
```

但该命令属于实施阶段设计，不在本 spec 中直接实现。

## 8. 焊缝技能单元设计方向

第二阶段不应直接从船舶构件名出发，而应建立 `WeldSkillUnit` 或等价概念，用来描述可迁移的焊接技能单元。

第一版分类维度建议：

| 维度 | 示例 |
| --- | --- |
| 焊缝几何 | 长直焊缝、U 型缝、包角、转角、短焊缝序列 |
| 接头形式 | 角焊、对接、T 型、坡口、搭接 |
| 焊接姿态 | 平焊、横焊、立焊、仰焊、混合姿态 |
| 运动结构 | 单段直线、多段折线、曲线、转角过渡、摆动轨迹 |
| 姿态约束 | 工作角、行进角、干伸长度、枪姿稳定性 |
| 过程参数 | 电流、电压、送丝、行走速度、热输入占位 |
| 机器人约束 | 可达性、碰撞、奇异点、关节限位、分段衔接 |
| 证据状态 | 公开资料约束、仿真假设、真机待验证、工艺评定待验证 |

这比 `stiffened-panel-fillet` 这类构件级场景更适合作为技能资产主线，因为同一技能单元可以在船舶、钢结构、重装、工程机械等多个行业复用。

`stiffened-panel-fillet` 可降级为某个技能单元的行业实例，而不是项目主线本体。

## 9. 类机器人仿真路线设计方向

下一阶段仿真路线应以机器人执行和机器人大脑训练为目标，但分层推进。

### 9.1 L0：几何与轨迹轻量仿真

用途：

- 保持当前测试稳定。
- 生成最小轨迹、姿态、过程信号。
- 验证 `SkillDataset`、`SimulationOutputBundle` 和 `WeldSkillPackage` 数据链路。

代表：

- 当前 simlite。

边界：

- 不证明机器人可达性。
- 不证明真实焊接质量。
- 不作为长期仿真主路线。

### 9.2 L1：机器人运动学、可达性与碰撞仿真

用途：

- 判断技能包是否能转化为机器人可执行动作。
- 检查 TCP 轨迹、姿态、关节限位、奇异点、碰撞和分段衔接。
- 为机器人执行建议提供证据。

代表候选：

- ROS 2 / MoveIt / Gazebo。
- Isaac Sim / Isaac Lab。
- SAPIEN。
- RoboDK 或其他离线编程/机器人仿真工具。

这是第二阶段最应优先调研和接入的仿真层。

### 9.3 L2：机器人任务学习与 demonstration 仿真

用途：

- 生成可用于机器人大脑训练的任务状态、动作、奖励、demonstration 或 evaluation benchmark。
- 让 `WeldSkillPackage` 与学习系统之间建立接口。

代表候选：

- ManiSkill。
- SAPIEN 任务环境。
- Isaac Lab。

边界：

- 不应一开始绑定某个生态。
- 必须能输出或转换为项目 canonical schema。

### 9.4 L3：焊接过程、热输入和质量物理仿真

用途：

- 后续研究真实焊接质量、热影响、成形、缺陷等。

当前边界：

- 不作为当前起点。
- 不进入第一阶段重构。
- 后续如果进入，必须和真实焊材、工艺评定、检测结果和专家审查绑定。

## 10. 资料调研路线设计

第二阶段资料调研应围绕技能资产和类机器人仿真，而不是无边界资料堆积。

优先资料方向：

1. 当前现场相关场景资料：中组立/类似构件焊接、U 型缝、包角、长直焊缝、横焊、立焊。
2. 焊接技能动作资料：摆动模板、枪姿、工作角、行进角、行走速度、停留、转角过渡。
3. 机器人执行资料：TCP 轨迹、姿态规划、可达性、碰撞、关节限位、分段焊接、离线编程。
4. 类机器人仿真资料：MoveIt/Gazebo、SAPIEN、ManiSkill、Isaac、RoboDK 等的输入输出能力。
5. 机器人大脑训练资料：demonstration、trajectory dataset、task benchmark、policy evaluation。
6. 质量边界资料：WPS/PQR、工艺评定、检测术语，只用于标注边界，不用于当前阶段质量声明。

每份资料进入项目时必须说明：

- 支持哪个技能单元。
- 支持哪个字段。
- 是公开约束、工程经验、仿真假设还是真实验证依据。
- 是否能进入 `WeldSkillPackage`。
- 是否能支持机器人执行或训练。
- 哪些结论不能写。

## 12. 风险与防偏规则

### 12.1 不要把归档写成否定前期成果

前期成果证明了轨迹结构化、技能包、迁移评测、资料 gate 和仿真输出接入能力。重构是重新归位，不是推翻。

### 12.2 不要让仿真器变成核心

ManiSkill、Isaac、SAPIEN、MoveIt、Gazebo、RoboDK 都只能作为 adapter 候选。核心问题始终是它们是否能服务 `WeldSkillPackage` 的训练、执行和证据链。

### 12.3 不要把构件级场景当作技能主线

船舶加筋板/纵骨角焊等构件级场景可以作为资料实例，但第一批技能资产应优先抽象为焊缝情况、姿态和动作技能单元。

### 12.4 不要把仿真结果写成真实质量结论

类机器人仿真可以证明可达性、姿态、轨迹、动作约束和接口能力，不能证明真实焊接质量。

### 12.5 不要把第一阶段变成长期大重构

第一阶段要让项目主线变清楚，并保持默认运行可用。实施时应分批移动和修改，避免一次性破坏测试、报告和路径引用。
