# 机器人上下文与可执行性预检接口设计

日期：2026-06-07

## 1. 背景

项目已经完成从仿真经验到机器人工艺候选包草案的第一层接口：

```text
WeldSkillUnit
-> SimulationTaskSpec
-> ManiSkill/SAPIEN lightweight spike 或 R0/simlite baseline
-> raw artifact
-> adapter result
-> ExperienceDataset / SkillDataset compatibility export
-> SimulationEvidenceBundle
-> RobotProcessPackageDraft
```

当前 `RobotProcessPackageDraft` 能明确表达哪些信息来自仿真、哪些信息缺失、哪些内容需要专家审查或真实机器人验证。这个边界是正确的，但它也暴露出下一处断点：多数草案会停在 `blocked_by_missing_robot_context`。

这个状态不是失败，而是系统在诚实地说明：仿真轨迹和姿态已经存在，但缺少机器人型号、TCP 标定、工件坐标系、可达性、碰撞和关节边界等执行上下文。因此下一阶段不应继续扩大仿真规模，也不应立刻接完整 Gazebo/MoveIt 或真实机器人控制，而应先建立一层稳定的机器人上下文与可执行性预检接口。

本设计延续上一阶段原则：主数据来源仍是仿真 evidence，人工工艺参数表只作为字段分组参考，不成为主流程输入。专家审查、真实机器人日志、焊机过程数据和质量反馈仍是后续来源，不在本阶段实现。

## 2. 目标

建立一条最小、可测试、面向未来 adapter 的机器人上下文预检链路：

```text
SimulationEvidenceBundle
-> RobotProcessPackageDraft
+ RobotContextSpec
-> RobotFeasibilityResult
-> updated RobotProcessPackageDraft
```

本阶段目标是：

1. 定义机器人上下文如何进入系统。
2. 定义可达性、碰撞、关节限制、路径连续性和姿态可行性预检结果如何表达。
3. 支持一个虚拟机器人上下文，例如 `mock_6axis_welding_robot`，用于默认测试和 pipeline 演示。
4. 让 `RobotProcessPackageDraft` 在上下文足够且预检通过时，从 `blocked_by_missing_robot_context` 推进到 `ready_for_expert_review`。
5. 为未来 MoveIt/Gazebo adapter 留出结果接口，但不把 MoveIt/Gazebo 加入默认依赖。

本阶段终点是“可审查的机器人执行候选判断”，不是“机器人可执行工艺包”。

## 3. 不做事项

本阶段明确不做：

- 不接真实机器人、PLC、焊机或现场总线。
- 不生成机器人程序、离线编程文件、G-code、URScript 或厂商控制器代码。
- 不安装或强依赖 MoveIt、Gazebo、ROS、Isaac、RoboDK、RobotStudio 或 Process Simulate。
- 不实现完整 IK、运动规划、碰撞几何或物理仿真。
- 不扩大 ManiSkill/SAPIEN 仿真规模。
- 不证明真实焊接质量。
- 不生成或替代 WPS/PQR。
- 不实现完整专家审核工作流。
- 不把虚拟机器人上下文写成真实设备能力结论。

## 4. 设计原则

### 4.1 结构接口优先

第一版先定义稳定对象和转换逻辑，让系统能表达“机器人上下文是否足够”和“预检结果是否允许进入专家审查”。对象应保持小而清晰，优先服务当前 pipeline，不引入大规模机器人抽象。

### 4.2 面向 MoveIt/Gazebo 预留

虽然第一版不接 MoveIt/Gazebo，但字段形状应让未来 adapter 能直接填充结果。例如可达性、碰撞、关节限制和路径连续性都应作为结构化状态，而不是散落在自由文本中。

### 4.3 不制造虚假执行结论

即使虚拟机器人上下文和轻量规则预检全部通过，本阶段也最多推进到：

```text
ready_for_expert_review
```

不得推进到：

```text
ready_for_robot_execution
```

真实机器人执行、焊机过程参数、焊接质量和工艺合规仍必须后续验证。

### 4.4 默认环境保持轻量

默认测试应只依赖现有 Python 项目环境。虚拟机器人上下文和轻量预检规则必须可在 `uv run pytest -q` 中稳定运行，不需要图形界面、机器人 middleware 或外部仿真器。

## 5. 核心对象

建议继续使用现有模块：

```text
weldcore.robot_process
```

不新增独立机器人控制模块。原因是本阶段仍属于“仿真经验到机器人候选包”的后半段，不是机器人控制系统。

### 5.1 RobotContextSpec

`RobotContextSpec` 表达一条候选草案要进入机器人侧预检时所需的执行上下文。

建议最小字段：

```text
context_id
robot_model
robot_family
base_frame
tcp_frame
tcp_calibration_status
workpiece_frame
tool_payload
joint_limits_source
workspace_hint
context_source
evidence_notes
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `context_id` | 上下文标识，例如 `mock-context-001` |
| `robot_model` | 机器人型号或虚拟型号，例如 `mock_6axis_welding_robot` |
| `robot_family` | 机器人族类，例如 `six_axis_industrial_arm` |
| `base_frame` | 机器人基坐标系 |
| `tcp_frame` | 工具中心点坐标系，应能与 task/evidence 中的 TCP 对齐 |
| `tcp_calibration_status` | TCP 是否已标定，第一版允许 `mock_calibrated` |
| `workpiece_frame` | 工件坐标系 |
| `tool_payload` | 工具负载摘要，可为结构化字典 |
| `joint_limits_source` | 关节限制来源，例如 `mock_spec`、`vendor_spec_later` |
| `workspace_hint` | 工作空间提示，例如最大半径、Z 范围或包围盒 |
| `context_source` | 来源，例如 `mock`、`manual_precheck`、`moveit_future` |
| `evidence_notes` | 证据边界说明 |

第一版必须提供一个默认虚拟上下文：

```text
mock_6axis_welding_robot
```

该上下文只用于测试和 pipeline 演示，必须带有 evidence boundary：

```text
mock_robot_context_only
not_real_robot_model
not_vendor_validated
not_ready_for_robot_execution
```

### 5.2 RobotFeasibilityProbe

`RobotFeasibilityProbe` 表达一次预检请求，把草案、机器人上下文和预检策略关联起来。

建议最小字段：

```text
probe_id
draft_id
context_id
strategy
requested_checks
adapter_hint
evidence_notes
```

`strategy` 第一版支持：

```text
manual_precheck
lightweight_rule
```

`adapter_hint` 预留：

```text
manual_precheck
lightweight_rule
moveit_future
gazebo_future
real_robot_future
```

`requested_checks` 第一版建议支持：

```text
reachability
collision
joint_limits
path_continuity
orientation_feasibility
```

### 5.3 RobotFeasibilityResult

`RobotFeasibilityResult` 表达预检结果。它是未来 MoveIt/Gazebo adapter 最应复用的对象。

建议最小字段：

```text
result_id
probe_id
draft_id
context_id
status
reachability_status
collision_status
joint_limit_status
path_continuity_status
orientation_feasibility_status
blocking_reasons
warning_reasons
evidence_source
adapter_hint
evidence_boundary
metrics
```

`status` 第一版支持：

```text
passed
failed
incomplete
```

各检查项状态支持：

```text
passed
failed
missing
not_checked
assumed
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `reachability_status` | 路径点是否在机器人工作空间内 |
| `collision_status` | 是否已发现碰撞风险 |
| `joint_limit_status` | 是否违反关节边界 |
| `path_continuity_status` | 路径是否连续、是否有明显断裂 |
| `orientation_feasibility_status` | 工具姿态序列是否完整且可审查 |
| `blocking_reasons` | 阻塞原因，决定 readiness 是否仍 blocked |
| `warning_reasons` | 非阻塞风险，例如 mock 证据边界 |
| `evidence_source` | 结果来源，例如 `lightweight_rule` |
| `adapter_hint` | 未来 adapter 线索 |
| `metrics` | 可选指标，例如路径点数量、最大工作半径估算 |

第一版轻量规则只允许基于已有结构做保守判断：

- trajectory 缺失：`reachability_status = missing`
- tool orientation 缺失：`orientation_feasibility_status = missing`
- robot context 缺失：整体 `status = incomplete`
- 虚拟上下文存在且轨迹/姿态存在：可输出 `passed`，但 evidence boundary 必须说明 mock 语义
- 不做真实几何碰撞，只能把 `collision_status` 标为 `assumed` 或 `not_checked`，除非输入显式提供失败结果

## 6. Readiness 更新规则

上一阶段 `RobotExecutionReadiness` 已包含：

```text
draft
needs_review
blocked_by_failed_simulation
blocked_by_missing_dataset
blocked_by_missing_trajectory
blocked_by_missing_orientation
blocked_by_missing_robot_context
ready_for_expert_review
ready_for_robot_execution
```

本阶段建议新增更细的阻塞状态：

```text
blocked_by_missing_robot_identity
blocked_by_missing_frame_context
blocked_by_missing_tcp_calibration
blocked_by_missing_feasibility_result
blocked_by_failed_reachability
blocked_by_failed_collision_check
blocked_by_failed_joint_limit_check
```

更新规则：

1. 仿真失败、缺 dataset、缺 trajectory、缺 orientation 时，沿用上一阶段阻塞逻辑。
2. 没有 `RobotContextSpec` 时，仍为 `blocked_by_missing_robot_context`。
3. 上下文缺机器人型号时，输出 `blocked_by_missing_robot_identity`。
4. 上下文缺 base/workpiece/TCP frame 时，输出 `blocked_by_missing_frame_context`。
5. TCP 标定状态缺失或为 unknown 时，输出 `blocked_by_missing_tcp_calibration`。
6. 上下文完整但没有 `RobotFeasibilityResult` 时，输出 `blocked_by_missing_feasibility_result`。
7. reachability/collision/joint limit 任一明确失败时，输出对应 failed 状态。
8. 上下文完整、轻量预检通过、且不存在阻塞原因时，输出 `ready_for_expert_review`。
9. 本阶段任何路径都不得输出 `ready_for_robot_execution`。

`ready_for_expert_review` 的含义是：

```text
仿真 evidence + 机器人上下文 + 轻量预检结果已经足够让专家审查候选包。
```

它不表示：

```text
机器人可以执行；
焊接工艺参数已经合格；
真实焊接质量已经验证；
WPS/PQR 已经成立。
```

## 7. Pipeline 设计

建议新增两个函数边界：

```text
build_robot_feasibility_result(draft, robot_context, strategy="lightweight_rule")
update_robot_process_draft_with_feasibility(draft, robot_context, feasibility_result)
```

第一版数据流：

```text
SimulationEvidenceBundle
-> build_robot_process_package_draft()
-> RobotProcessPackageDraft
-> default_mock_robot_context()
-> build_robot_feasibility_result()
-> update_robot_process_draft_with_feasibility()
-> RobotProcessPackageDraft(readiness="ready_for_expert_review" 或 blocked_*)
```

更新后的 draft 应保留原始仿真 evidence boundary，并追加机器人上下文/预检边界，例如：

```text
mock_robot_context_only
lightweight_feasibility_precheck_only
not_moveit_validated
not_gazebo_validated
not_real_robot_validated
not_ready_for_robot_execution
```

`RobotExecutionSpec` 应从 `RobotContextSpec` 和 `RobotFeasibilityResult` 回填：

- `robot_model`
- `workpiece_frame`
- `reachability_status`
- `collision_status`
- `joint_limit_status`
- `missing_robot_context`
- `execution_notes`

## 8. MoveIt/Gazebo Adapter 预留边界

本阶段不实现 MoveIt/Gazebo，但必须让下一阶段可以自然接入：

```text
MoveIt/Gazebo Adapter
-> RobotFeasibilityResult
```

未来 adapter 只需要负责把外部结果转换为统一对象：

- IK/可达性结果 -> `reachability_status`
- 碰撞检测结果 -> `collision_status`
- 关节限制检查 -> `joint_limit_status`
- 轨迹规划连续性 -> `path_continuity_status`
- 姿态约束检查 -> `orientation_feasibility_status`
- 失败原因 -> `blocking_reasons`
- 原始运行摘要 -> `metrics` 和 `evidence_boundary`

核心模型不应依赖 MoveIt/Gazebo 的对象类型、文件格式或安装路径。

## 9. 测试策略

第一版测试应覆盖：

1. `RobotContextSpec` 可以序列化为 dict。
2. 默认 `mock_6axis_welding_robot` 上下文包含必要 frame、robot model 和 mock evidence boundary。
3. 缺机器人上下文时，draft 仍停在 `blocked_by_missing_robot_context`。
4. 上下文缺 robot model 时，更新后 readiness 为 `blocked_by_missing_robot_identity`。
5. 上下文缺 frame 时，更新后 readiness 为 `blocked_by_missing_frame_context`。
6. 上下文缺 TCP 标定时，更新后 readiness 为 `blocked_by_missing_tcp_calibration`。
7. 上下文完整但没有 feasibility result 时，readiness 为 `blocked_by_missing_feasibility_result`。
8. reachability 明确失败时，readiness 为 `blocked_by_failed_reachability`。
9. collision 明确失败时，readiness 为 `blocked_by_failed_collision_check`。
10. joint limit 明确失败时，readiness 为 `blocked_by_failed_joint_limit_check`。
11. 使用默认 mock context 和通过的 lightweight result 时，draft 推进到 `ready_for_expert_review`。
12. 任何路径都不能产出 `ready_for_robot_execution`。
13. evidence boundary 必须保留 `not_ready_for_robot_execution`。
14. `uv run pytest -q` 在默认环境中通过。

## 10. 验收标准

本阶段完成后，应满足：

1. `weldcore.robot_process` 中存在机器人上下文和可执行性预检的最小模型。
2. 默认虚拟机器人上下文可以被 pipeline 使用。
3. 现有 `RobotProcessPackageDraft` 可以被机器人上下文和预检结果更新。
4. 完整 mock 上下文 + 通过的轻量预检可以把 readiness 推进到 `ready_for_expert_review`。
5. 缺字段、缺预检和预检失败会产出明确 blocked 状态。
6. `ready_for_robot_execution` 仍不可达。
7. 不新增 MoveIt/Gazebo/ROS/真实机器人依赖。
8. 默认测试命令通过。

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| mock 上下文被误读为真实机器人能力 | evidence boundary 明确写入 `mock_robot_context_only` 和 `not_real_robot_model` |
| 轻量预检被误读为真实可执行性验证 | readiness 最高只到 `ready_for_expert_review` |
| 字段过度面向 MoveIt/Gazebo，导致第一版复杂 | 只保留 status、reason、metrics 三类接口，不引入外部对象 |
| readiness 状态膨胀 | 只新增当前断点必须区分的状态，避免提前建完整执行状态机 |
| 未来 adapter 返工 | `RobotFeasibilityResult` 作为 adapter 输出契约，核心模型不绑定外部工具 |

## 12. 后续路线

完成本阶段后，下一步建议进入：

```text
MoveIt/Gazebo adapter spike
```

该阶段只做一条最小 adapter，把真实或半真实机器人规划工具的输出转换为 `RobotFeasibilityResult`，验证当前接口是否足够承接 IK、碰撞和关节限制结果。

再下一阶段可以进入：

```text
Robot process package report/export
ExpertReviewRecord
```

届时专家审查的对象将不再是松散数据，而是：

```text
SimulationEvidenceBundle
+ RobotProcessPackageDraft
+ RobotContextSpec
+ RobotFeasibilityResult
```

这会让专家审查更接近产品核心：审查候选工艺包和机器人可执行性证据，而不是管理流程表单。

## 13. 推荐实施拆分

后续实施计划建议分为四个任务：

1. 添加 `RobotContextSpec`、`RobotFeasibilityProbe`、`RobotFeasibilityResult` 模型和序列化测试。
2. 添加默认 `mock_6axis_welding_robot` 上下文和轻量预检结果生成函数。
3. 添加 draft 更新函数和 readiness 状态推进逻辑。
4. 更新 README 或 report 边界说明，明确本阶段仍不是真实机器人执行验证。
