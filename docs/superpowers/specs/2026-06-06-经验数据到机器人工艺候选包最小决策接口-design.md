# 经验数据到机器人工艺候选包最小决策接口设计

日期：2026-06-06

## 1. 背景

项目当前已经完成前半段仿真经验闭环：

```text
WeldSkillUnit
-> SimulationTaskSpec
-> ManiSkill/SAPIEN lightweight spike 或 R0/simlite baseline
-> raw artifact
-> adapter result
-> ExperienceDataset / SkillDataset compatibility export
-> SimulationEvidenceBundle
```

这个闭环已经能把仿真任务、轨迹、姿态、任务状态、失败边界和证据包组织起来。但它还没有进入后半段接口：

```text
ExperienceDataset / SimulationEvidenceBundle
-> robot execution candidate
-> robot process package draft
-> expert review / real robot validation later
```

下一轮不应急着扩大仿真规模，也不应直接接 Gazebo/MoveIt 或真实机器人控制。当前更重要的是把仿真经验数据接到未来机器人可执行工艺包的前置决策接口上，让系统知道：哪些信息已经来自仿真，哪些信息缺少机器人上下文，哪些需要专家审查，哪些必须真机和质量验证。

工程师提供的 `docs/焊接工艺数据库主要参数表.xlsx` 只作为字段分类参考。该表覆盖母材、焊材、接头、焊接方法、焊接参数、气体参数、质量要求和工艺规程关联等参数，并标记了必填、条件必填和可选字段。第一版设计不能全盘接收这些字段，也不能把表格内容当成当前项目已经具备的工艺数据来源。它只帮助我们区分字段来源、缺口和验证状态。

## 2. 目标

建立一条最小代码级决策接口：

```text
SimulationEvidenceBundle
-> RobotProcessPackageDraft
-> RobotExecutionReadiness
```

本阶段目标是：

1. 从现有仿真 evidence 生成机器人工艺候选包草案。
2. 明确区分仿真可提供的信息、缺失的机器人上下文、未来专家审查项和未来真机验证项。
3. 为后续 `RobotExecutionSpec`、专家审核、真实机器人日志、焊机过程数据和质量反馈留下稳定接口。
4. 保持默认项目环境轻量、可测试，不引入新的仿真器或机器人依赖。

本阶段终点不是机器人可执行工艺包，而是机器人执行前的草案级决策接口。

## 3. 不做事项

本阶段明确不做：

- 不扩大 ManiSkill/SAPIEN 仿真规模。
- 不接 Gazebo/MoveIt、ROS、真实机器人、焊机、PLC 或现场总线。
- 不接人工工艺参数 JSON 作为主流程输入。
- 不实现完整专家审核工作流。
- 不生成机器人程序、离线编程文件或真实设备调用指令。
- 不生成或替代 WPS/PQR。
- 不证明真实焊接质量。
- 不把工程师参数表硬编码为完整 schema。
- 不把仿真经验写成可生产工艺结论。

## 4. 主输入与来源边界

第一版主输入固定为：

```text
SimulationEvidenceBundle
```

它当前包含：

```text
SimulationTaskSpec
SimulatorAdapterResult
SimulationRunRecord
SkillDataset | None
rerun replay status
bakeoff score
failure boundary
```

第一版只支持 `source_type = simulation`。未来可扩展的数据来源包括：

```text
simulation
expert_review
real_robot_log
welder_process_data
quality_feedback
```

这些来源只在 evidence boundary 和字段状态中预留，不在第一版 pipeline 中实现。

## 5. 核心对象

建议新增一个小模块：

```text
weldcore.robot_process
```

该模块不属于 `simulation_bakeoff`，因为它表达的是仿真之后、机器人执行之前的工艺-执行候选包边界。第一版转换函数只接受 `SimulationEvidenceBundle`，但模块位置应允许后续接专家、真机和质量反馈。

### 5.1 RobotProcessPackageDraft

`RobotProcessPackageDraft` 是聚合对象，代表一条仿真经验是否能形成未来可审查、可验证、可迁移到机器人侧的候选包草案。

最小字段：

```text
draft_id
source_bundle_id
source_task_id
source_type
status
source_evidence
process_parameter_status
robot_execution_spec
readiness
evidence_boundary
```

第一版 `status` 固定为草案类状态，例如：

```text
draft
blocked
```

不能产出生产、发布、approved 或 executable 类状态。

### 5.2 RobotExecutionSpec

`RobotExecutionSpec` 只表达机器人执行前置上下文，不承接完整工艺数据库。

最小字段：

```text
robot_model
tcp_frame
workpiece_frame
trajectory
tool_orientation
travel_speed
reachability_status
collision_status
joint_limit_status
execution_notes
missing_robot_context
```

第一版可从仿真 evidence 中得到：

- `tcp_frame`
- `trajectory`
- `tool_orientation`
- 部分 motion metrics 或 task status

第一版通常缺失：

- 真实机器人型号
- TCP 标定
- 工件坐标系
- IK 可达性
- 碰撞结果
- 关节边界
- 真实执行验证状态

因此第一版不允许输出 `ready_for_robot_execution`。

### 5.3 RobotExecutionReadiness

`RobotExecutionReadiness` 表达当前草案距离下一步动作的状态。

建议状态：

```text
draft
needs_review
blocked_by_failed_simulation
blocked_by_missing_dataset
blocked_by_missing_trajectory
blocked_by_missing_orientation
blocked_by_missing_robot_context
ready_for_expert_review
ready_for_robot_execution
```

第一版可以产出：

```text
draft
blocked_by_failed_simulation
blocked_by_missing_dataset
blocked_by_missing_trajectory
blocked_by_missing_orientation
blocked_by_missing_robot_context
```

第一版预留但不能产出：

```text
needs_review
ready_for_expert_review
ready_for_robot_execution
```

`needs_review` 和 `ready_for_expert_review` 在第一版只作为枚举值保留，不实现可达分支，也不写对应测试。原因是当前主输入只有仿真 evidence，还缺少机器人型号、工件坐标系、TCP 标定、可达性、碰撞和关节边界等机器人上下文；在这些前置证据缺失时，草案最多只能到 `blocked_by_missing_robot_context`。

### 5.4 ProcessParameterStatus

`ProcessParameterStatus` 不保存完整工程参数表，而是按分组表达字段状态。

建议分组：

```text
motion_parameters
process_parameters
material_parameters
joint_parameters
gas_parameters
quality_requirements
procedure_links
robot_context
validation_requirements
```

每组最小字段：

```text
group_name
statuses
available_fields
missing_fields
required_future_sources
evidence_notes
```

`statuses` 是多值集合，因为同一组参数可能同时具备多个判断。例如 `process_parameters` 可以同时是 `missing_required`、`requires_expert_review` 和 `requires_real_validation`。

字段状态枚举建议：

```text
available_from_simulation
partially_available_from_simulation
missing_required
conditionally_missing
optional_missing
requires_expert_review
requires_real_validation
requires_robot_context
not_applicable
out_of_scope_now
not_WPS_PQR
```

工程师参数表中的“必填 / 条件必填 / 可选”只影响这里的缺口状态：

```text
必填 -> statuses 包含 missing_required，并在 required_future_sources 记录未来来源
条件必填 -> statuses 包含 conditionally_missing 或 not_applicable，并在需要时记录 required_future_sources
可选 -> optional_missing
```

它不要求第一版 pipeline 填满这些字段。

## 6. Pipeline 设计

第一版只需要一个主函数：

```text
build_robot_process_package_draft(evidence_bundle)
```

流程：

```text
SimulationEvidenceBundle
-> 读取 task_spec / adapter_result / dataset / run_record
-> 判断仿真是否 completed
-> 抽取轨迹、姿态、任务状态、metrics、failure_boundary
-> 生成 process_parameter_status
-> 生成 robot_execution_spec
-> 生成 readiness
-> 输出 RobotProcessPackageDraft
```

### 6.1 仿真失败

如果：

```text
adapter_result.status != "completed"
```

则：

```text
readiness = blocked_by_failed_simulation
robot_execution_spec.trajectory = empty
process_parameter_status 记录失败边界和来源缺口
```

失败仿真也应生成 draft，因为失败边界本身是证据。但该 draft 不能进入专家审核或机器人执行候选。

### 6.2 数据集缺失

如果：

```text
adapter_result.status == "completed"
dataset is None
```

则：

```text
readiness = blocked_by_missing_dataset
```

这表示 adapter 可能完成了任务，但没有形成后续可消费的数据资产。

### 6.3 轨迹或姿态缺失

如果：

```text
tcp_trajectory 为空
```

则：

```text
readiness = blocked_by_missing_trajectory
```

如果：

```text
tool_orientation 为空
```

则：

```text
readiness = blocked_by_missing_orientation
```

轨迹和姿态是机器人执行候选包的最小前提。

### 6.4 机器人上下文缺失

如果仿真完成且数据集存在，但缺少：

```text
robot_model
workpiece_frame
tcp calibration
reachability result
collision result
joint limit result
```

则：

```text
readiness = blocked_by_missing_robot_context
```

这是第一版最常见的成功仿真后状态。它表示仿真经验可以进入后半段接口，但不能进入机器人执行。

### 6.5 可进入专家审查

未来如果 evidence 中包含足够机器人上下文，但仍缺少工艺参数、质量验证或专家确认，则可进入：

```text
readiness = ready_for_expert_review
```

第一版只预留这一状态，不实现可达分支。实现计划不应为 `ready_for_expert_review` 编写通过当前 evidence 达到该状态的测试；该状态留到后续接入机器人上下文或专家审核入口时再启用。

### 6.6 Readiness 优先级

当多个阻断条件同时出现时，readiness 按以下顺序判定，命中后即停止：

```text
adapter_result.status != "completed"
-> blocked_by_failed_simulation

dataset is None
-> blocked_by_missing_dataset

tcp_trajectory 为空
-> blocked_by_missing_trajectory

tool_orientation 为空
-> blocked_by_missing_orientation

缺少机器人上下文
-> blocked_by_missing_robot_context

其他情况
-> draft
```

第一版不通过当前转换函数产出 `needs_review`、`ready_for_expert_review` 或 `ready_for_robot_execution`。

## 7. 参数分组映射

第一版不硬编码工程师表格全部字段，只保留最小分组和典型字段状态。`process_parameter_status` 应实现为分组记录列表或 tuple，而不是单个对象；每个分组记录通过 `group_name` 标识自身。实现时可以额外提供按 `group_name` 查询的 helper，但核心序列化结果应保持为分组记录列表。

### 7.1 motion_parameters

来自仿真 evidence：

- seam path / tcp trajectory
- tool orientation
- motion constraint
- path continuity
- posture stability
- task status

`statuses` 通常为：

```text
available_from_simulation
```

### 7.2 process_parameters

对应焊接电流、电压、焊接速度、送丝速度、热输入、摆弧宽度、摆弧频率、焊枪角度、干伸长、预热温度、层间温度等。

第一版 `statuses` 通常为：

```text
missing_required
requires_expert_review
requires_real_validation
```

其中运动速度或路径连续性可来自仿真，但不能等同真实工艺速度和热输入结论。

### 7.3 material_parameters

对应母材牌号、厚度、材质标准、化学成分、力学性能等。

第一版 `statuses` 通常为：

```text
missing_required
requires_expert_review
```

### 7.4 joint_parameters

对应接头类型、坡口形式、坡口角度、根部间隙、钝边、衬垫、焊脚尺寸等。

第一版可从 `SimulationTaskSpec.unit_id` 获得粗粒度任务语义，但不能替代真实接头参数。

`statuses` 通常为：

```text
partially_available_from_simulation
requires_expert_review
```

### 7.5 gas_parameters

对应保护气体类型、气体组分、气体流量、背面保护气等。

第一版 `statuses` 通常为：

```text
conditionally_missing
requires_expert_review
```

### 7.6 quality_requirements

对应外观检验标准、无损检测方法、无损检测等级、密性试验要求等。

第一版 `statuses` 通常为：

```text
requires_real_validation
```

### 7.7 procedure_links

对应 WPS 编号、PQR 编号、适用设备型号、适用车间/产线等。

第一版 `statuses` 通常为：

```text
missing_required
not_WPS_PQR
requires_expert_review
```

即使未来记录 WPS/PQR 编号，也只能作为引用，不能由系统自动生成或替代正式 WPS/PQR。

### 7.8 robot_context

对应机器人型号、TCP、坐标系、可达性、碰撞、关节边界、执行约束。

第一版 `statuses` 通常为：

```text
requires_robot_context
```

### 7.9 validation_requirements

对应专家审查、真实机器人执行、焊机过程数据、质量反馈和边界说明。

第一版 `statuses` 通常为：

```text
requires_expert_review
requires_real_validation
```

## 8. Evidence Boundary

每个 `RobotProcessPackageDraft` 必须携带 evidence boundary。

第一版固定包含：

```text
simulation_only
not_robot_process_package
not_ready_for_robot_execution
not_real_welding_quality_validation
not_WPS_PQR
requires_expert_review_later
requires_real_robot_validation_later
```

如果来源 evidence 已失败，还应包含对应 `failure_boundary`。

这些边界用于阻止系统把仿真经验误写成生产工艺、机器人程序、真实质量结论或 WPS/PQR。

## 9. 错误处理

第一版不需要复杂异常体系。业务状态应尽量落到 readiness 和 evidence boundary 中。

建议规则：

```text
evidence_bundle.dataset is None
-> blocked_by_failed_simulation 或 blocked_by_missing_dataset

adapter_result.status == failed
-> blocked_by_failed_simulation

adapter_result.tcp_trajectory 为空
-> blocked_by_missing_trajectory

adapter_result.tool_orientation 为空
-> blocked_by_missing_orientation

缺少机器人型号 / 工件坐标系 / TCP 标定 / 可达性 / 碰撞结果
-> blocked_by_missing_robot_context

仿真成功但工艺参数、材料、焊材、气体、质量要求缺失
-> 仍生成 draft，但 process_parameter_status 的对应分组在 statuses 中标记缺口，并在 required_future_sources 中记录未来来源
```

核心原则：

```text
工艺参数缺失不阻断 draft 生成；
机器人执行上下文缺失阻断执行 readiness；
仿真失败生成 blocked draft；
质量验证和 WPS/PQR 永远不能由本阶段自动满足。
```

## 10. 测试策略

新增测试建议：

```text
weld-experience-engine/tests/test_robot_process_models.py
weld-experience-engine/tests/test_robot_process_pipeline.py
```

覆盖：

1. `RobotProcessPackageDraft` 可以序列化为 dict。
2. completed `SimulationEvidenceBundle` 可以生成 draft。
3. failed `SimulationEvidenceBundle` 可以生成 `blocked_by_failed_simulation` draft。
4. completed evidence 缺少机器人上下文时生成 `blocked_by_missing_robot_context`。
5. 缺少 trajectory 时生成 `blocked_by_missing_trajectory`。
6. 缺少 orientation 时生成 `blocked_by_missing_orientation`。
7. `process_parameter_status` 包含 motion、process、material、joint、gas、quality、procedure、robot、validation 分组。
8. `evidence_boundary` 包含 `simulation_only`、`not_WPS_PQR`、`not_real_welding_quality_validation` 和 `not_ready_for_robot_execution`。
9. pipeline 不要求人工参数 JSON。
10. 默认 `uv run pytest -q` 仍可通过，不需要 ManiSkill/SAPIEN、Gazebo/MoveIt 或 Rerun。

## 12. 成功标准

本设计对应实现完成后，应满足：

1. 默认测试通过。
2. 不引入新的仿真器、机器人、Rerun 或表格解析依赖。
3. pipeline 主输入只接受 `SimulationEvidenceBundle`。
4. 能从现有 simlite completed evidence 生成 draft。
5. 能从 failed external evidence 生成 blocked draft。
6. 输出明确区分仿真来源、缺失机器人上下文、未来专家审查和未来真机验证。
7. 不声称已生成机器人可执行工艺包。
8. 不声称真实焊接质量验证。
9. 不生成或替代 WPS/PQR。
10. 工程师参数表只作为字段分类参考，不作为第一版硬 schema。

## 13. 后续决策门

本阶段完成后，再判断下一轮方向：

- 如果 draft 结构稳定，下一步可做 `ExpertReviewRecord` 的最小审核记录。
- 如果机器人上下文成为主要缺口，下一步可做 Gazebo/MoveIt 或工业离线编程侧线的最小可达性验证。
- 如果仿真 evidence 太薄，下一步再扩展 ManiSkill/SAPIEN task outputs 和小批量数据生成。
- 如果工艺参数字段成为主瓶颈，再设计可选的人工参数 overlay 或工艺资料导入接口。

当前不应提前实现这些后续方向。

## 14. 设计验证口径

检查本设计是否成立时，重点看：

- 是否保持仿真 evidence 为第一版唯一主输入。
- 是否避免人工参数资料喧宾夺主。
- 是否建立了从经验数据到机器人执行候选包的后半段接口。
- 是否明确阻止仿真经验被写成机器人可执行工艺包。
- 是否保留专家、真机、焊机过程数据和质量反馈的未来位置。
- 是否保持模块小、边界清楚、默认测试轻量。
