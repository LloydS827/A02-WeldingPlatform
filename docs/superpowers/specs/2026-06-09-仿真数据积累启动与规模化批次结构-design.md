# 仿真数据积累启动与规模化批次结构设计

日期：2026-06-09

## 1. 背景

项目已经完成从 `WeldSkillUnit` 到 ManiSkill/SAPIEN 小批量默认仿真入口的前半段链路：

```text
WeldSkillUnit
-> SimulationTaskSpec
-> ManiSkill/SAPIEN lightweight run
-> raw artifact
-> SimulatorAdapterResult
-> experience dataset
-> SimulationEvidenceBundle
-> SimulationBatchResult
```

上一轮已经新增 `SimulationBatchSpec`、`SimulationSamplePlan`、`SimulationSampleRun` 和 `SimulationBatchResult`，默认支持 2 个任务 x 10 条 primary 样本的批量运行契约。每条样本可以独立落盘 raw artifact、adapter result、experience dataset、evidence bundle 或 failure artifact，单条失败不会中断整个 batch。

下一阶段不再停留在“是否准备好积累数据”的前置报告，也不继续只做小规模接口演示。项目需要进入 **通过仿真开始积累数据** 的阶段，同时把后续扩大到 500、1000+ 样本时需要的批次管理、索引和状态判断接口先建立起来。

这一轮的核心判断是：现在已经有足够的 batch 入口，可以开始积累数据；但仍不能把 ManiSkill/SAPIEN 写成最终仿真器选型，也不能把仿真样本写成真实焊接质量验证。

## 2. 设计目标

本阶段目标是建立 **仿真数据积累启动层**。

它要回答：

1. 如何表达一次面向数据资产积累的仿真活动，而不只是一次小批量运行。
2. 如何把现有 ManiSkill/SAPIEN batch 输出汇总为可检索、可追踪、可复跑的 dataset index。
3. 如何在样本成功、失败、跳过并存时判断当前是否已经进入数据积累状态。
4. 如何把失败边界转化为下一轮扩大规模前的工程约束，而不是把失败简单视为项目失败。
5. 如何明确 100、500、1000+ 样本的分阶段扩展方式。
6. 如何保持当前默认运行路径稳定，不因扩大野心而破坏已有测试和命令。

本阶段不是最终仿真器选型，不做真实机器人执行，不做焊接质量结论，不做分布式调度系统，也不引入真实 WPS/PQR 口径。

## 3. 阶段位置

当前路线更新为：

```text
第一轮：统一 adapter facade / registry
第二轮：ManiSkill/SAPIEN 小批量默认入口
第三轮：仿真数据积累启动层
第四轮：规模化仿真运行与入口条件性锁定
```

本 spec 覆盖第三轮。

第三轮完成后，项目应具备：

- 可以启动第一轮仿真数据积累的命令或函数入口。
- 可以描述一次 accumulation run 的 spec。
- 可以从 batch result 汇总 dataset index。
- 可以输出 accumulation report，说明当前积累状态、完成样本、失败边界和下一轮规模化条件。
- 可以保留 failure samples 作为反证数据，而不是只保留成功样本。

第四轮再根据第三轮产物推进更大规模运行、分片、恢复和条件性入口锁定。

## 4. 核心口径：积累活动优先

上一轮的基本单位是 sample run：

```text
one task
+ one route
+ one seed
+ one variation policy
-> one run attempt
```

本阶段的基本单位提升为 accumulation run：

```text
one accumulation_id
+ one or more batch_id
+ one route
+ selected tasks
+ target requested samples
-> dataset index
-> accumulation report
```

这意味着本阶段不只关心“某个 batch 是否跑完”，而是关心这些 batch 是否开始形成可持续积累的数据资产。

第一版允许只由一个底层 batch 构成一个 accumulation run。这样可以直接复用现有 pipeline，不急于引入复杂调度。后续当目标规模进入 500 或 1000+ 样本时，再把一个 accumulation run 拆成多个 batch shard。

## 5. 第一轮数据规模

第一轮数据积累建议采用比上一轮更有野心、但仍可控的规模：

- route：`maniskill_sapien`
- task：沿用 2 个默认 `SimulationTaskSpec`
  - `task-long-straight-horizontal-tracking`
  - `task-corner-horizontal-transition`
- 每个 task：50 条 requested samples
- 总请求样本数：100

这个规模的目的不是追求统计充分性，而是让系统第一次经历“数据积累”的真实形态：

- 文件数量明显超过演示样本。
- 成功、失败、跳过都必须可索引。
- 环境缺失或 adapter 失败会产生足够多的 failure boundary 证据。
- 下游可以开始讨论字段覆盖、任务覆盖和下一轮 scale plan。

第三个 `WeldSkillUnit` 暂不作为第一轮积累默认对象。它可以作为第四轮扩展对象，避免在积累层刚建立时同时扩大任务复杂度和样本规模。

## 6. 核心组件

### 6.1 SimulationAccumulationBatchSpec

表达一次数据积累活动。

建议字段：

- `accumulation_id`
- `route_id`
- `task_specs`
- `samples_per_task`
- `target_requested_sample_count`
- `batch_id_prefix`
- `output_root`
- `seed_start`
- `variation_policy`
- `scale_phase`
- `scale_plan`
- `resume_policy`
- `stage_boundary`

第一版默认：

```text
route_id = "maniskill_sapien"
samples_per_task = 50
target_requested_sample_count = 100
scale_phase = "phase_1_accumulation_start"
resume_policy = "reuse_existing_batch_result_unless_force"
stage_boundary = "simulation_accumulation_not_real_welding_quality"
```

`SimulationAccumulationBatchSpec` 不替代 `SimulationBatchSpec`。它是更高一层的管理对象，负责说明为什么要跑这一组 batch、目标规模是多少、输出如何索引、下一步如何扩展。

`target_requested_sample_count` 第一版应由 `len(task_specs) * samples_per_task` 派生，并在序列化输出中记录派生结果。若调用方显式传入的 `target_requested_sample_count` 与派生值不一致，应直接报错，而不是悄悄覆盖或只作为松散元数据保留。这样可以避免 accumulation report 中的完成率和 batch result 中的 requested count 发生口径冲突。

### 6.2 SimulationDatasetIndex

表达一次 accumulation run 产生的数据资产索引。

建议字段：

- `accumulation_id`
- `route_id`
- `batch_ids`
- `requested_sample_count`
- `completed_sample_count`
- `failed_sample_count`
- `skipped_sample_count`
- `index_items`
- `failure_boundaries`
- `dataset_uris`
- `evidence_bundle_uris`
- `batch_root_uris`
- `batch_result_uris`
- `field_coverage_summary`
- `created_at`

`index_items` 每条记录建议包含：

- `accumulation_id`
- `batch_id`
- `sample_id`
- `task_id`
- `route_id`
- `seed`
- `variation_policy`
- `status`
- `raw_artifact_uri`
- `adapter_result_uri`
- `experience_dataset_uri`
- `evidence_bundle_uri`
- `failure_boundary`
- `failure_artifact_uri`

URI 归一化规则：

- `SimulationDatasetIndex` 必须记录每个 `batch_id` 对应的 `batch_root_uri` 和 `batch_result_uri`。
- `index_items` 中的 artifact URI 第一版采用 **相对 batch root 的 URI**，沿用当前 `SimulationSampleRun` 的样本级输出口径。
- 消费方需要定位文件时，应通过 `batch_root_uri + item.uri` 解析完整路径。
- 若后续 accumulation runner 把 batch 目录嵌入 accumulation 目录，仍然按上述规则记录；此时 `batch_root_uri` 指向嵌入后的 batch 根目录。
- 不在 index item 中混用绝对路径、相对 accumulation root 路径和相对 batch root 路径。

第一版 `field_coverage_summary` 可以保持轻量，只统计关键 URI 是否存在：

- raw artifact 是否存在。
- adapter result 是否存在。
- evidence bundle 是否存在。
- experience dataset 是否存在。
- failure artifact 是否存在。

统计口径应同时给出 requested-sample 视角和 completed-sample 视角：

- `requested_sample_coverage`：以全部 requested samples 为分母，反映整体积累链路覆盖情况。
- `completed_sample_coverage`：只以 completed samples 为分母，反映成功数据资产内部字段完整性。

不在本阶段实现复杂字段级质量评分，避免把数据积累启动层做成重型数据治理系统。

### 6.3 SimulationAccumulationReport

表达一次 accumulation run 的状态判断和下一步建议。

建议字段：

- `accumulation_id`
- `status`
- `requested_sample_count`
- `completed_sample_count`
- `failed_sample_count`
- `skipped_sample_count`
- `completion_ratio`
- `dominant_failure_boundaries`
- `dataset_index_uri`
- `batch_result_uris`
- `readiness_for_next_scale`
- `next_scale_recommendation`
- `known_limitations`

建议状态：

- `accumulating_completed_samples`：已有可用 completed samples，数据资产开始形成。
- `accumulating_with_failures`：已有 completed samples，同时存在失败样本，需要带条件继续。
- `blocked_by_environment`：核心环境缺失或所有样本都无法进入可用数据链路。
- `ready_to_scale_with_conditions`：完成样本和失败边界足以支持下一轮扩大规模，但仍有明确条件。

状态判断口径：

- 状态判断必须按固定优先级执行，避免同一批结果被归入多个状态。
- 第一优先级：若 requested sample > 0、completed sample = 0，且 failure boundary 包含 `environment_missing`，状态为 `blocked_by_environment`。
- 第二优先级：若 completed sample > 0，且 failed sample 或 skipped sample > 0，状态为 `accumulating_with_failures`。
- 第三优先级：若 completed sample = requested sample，failed sample = 0，skipped sample = 0，且 `failure_boundaries` 为空，状态为 `ready_to_scale_with_conditions`。
- 第四优先级：若 completed sample > 0，且尚未达到第三优先级，状态为 `accumulating_completed_samples`。

第一版的 scale-ready 阈值就是 `completed_sample_count == requested_sample_count`。这里的 `with_conditions` 指仿真数据仍受 stage boundary、任务覆盖和真实焊接验证缺失约束，不表示可以忽略失败样本直接扩大规模。

本阶段的结构性 failure boundary 集合与样本级 failure boundary 保持一致，包括：

- `task_generation_failed`
- `demo_generation_failed`
- `simulation_run_failed`
- `adapter_conversion_failed`
- `experience_dataset_export_failed`
- `evidence_export_failed`
- `environment_missing`
- `data_contract_incomplete`

第一版不需要给出复杂评分。它只需要给出工程判断：已经积累、带失败积累、被环境阻塞、或可以带条件扩大。

## 7. 数据流

主数据流：

```text
SimulationAccumulationBatchSpec
-> derive SimulationBatchSpec
-> run_maniskill_batch_pipeline()
-> batch_spec.json
-> batch_result.json
-> SimulationDatasetIndex
-> dataset_index.json
-> SimulationAccumulationReport
-> accumulation_report.json
```

第一版应尽量复用现有 `run_maniskill_batch_pipeline`，只做必要扩展：

- 允许传入 `samples_per_task`，默认仍保持上一轮的 10。
- 允许传入 `seed_start`，默认仍保持 0。
- 允许传入或派生 `batch_id`。
- 保持现有 CLI 默认行为不变，避免破坏 README 中的小批量命令。

新的 accumulation runner 可以在内部调用扩展后的 batch pipeline，生成一个 100 requested samples 的 accumulation run。

建议新增 CLI：

```bash
uv run python -m weldcore.simulation_bakeoff.maniskill_accumulation_pipeline \
  --outdir artifacts/simulation/maniskill-sapien-accumulations
```

该 CLI 默认生成 Phase 1 的 100 requested samples 口径。现有 `weldcore.simulation_bakeoff.maniskill_batch_pipeline` CLI 默认仍保持 2 个任务 x 10 samples，不因本阶段新增积累入口而改变。

建议默认输出：

```text
artifacts/simulation/maniskill-sapien-accumulations/
└── {accumulation_id}/
    ├── accumulation_spec.json
    ├── dataset_index.json
    ├── accumulation_report.json
    └── batches/
        └── {batch_id}/
            ├── batch_spec.json
            ├── batch_result.json
            └── samples/
                └── {sample_id}/
                    ├── task_config.json
                    ├── demo.json
                    ├── raw_artifact.json
                    ├── adapter_result.json
                    ├── experience_dataset.json
                    ├── evidence_bundle.json
                    └── failure_artifact.json
```

若复用现有 batch 输出目录会明显降低实现成本，也可以第一版采用：

```text
artifacts/simulation/maniskill-sapien-accumulations/{accumulation_id}/
artifacts/simulation/maniskill-sapien-batches/{batch_id}/
```

但 `dataset_index.json` 必须记录 batch result 的真实 URI，避免跨目录后无法追踪。

## 8. 失败边界

本阶段继续采用样本级失败边界。

必须保留的原则：

- 单条样本失败不能中断 accumulation run。
- 失败样本必须进入 dataset index。
- 失败样本可以没有 experience dataset，但必须尽量有 failure artifact。
- 如果 failure artifact 也无法写入，仍要用 sentinel 记录 `data_contract_incomplete`。
- accumulation report 不应隐瞒失败数量。

常见 failure boundary：

- `task_generation_failed`
- `demo_generation_failed`
- `simulation_run_failed`
- `adapter_conversion_failed`
- `experience_dataset_export_failed`
- `evidence_export_failed`
- `environment_missing`
- `data_contract_incomplete`

环境缺失的判断要特别谨慎。若本机缺少 ManiSkill/SAPIEN 环境，accumulation runner 仍应完成索引和报告输出，只是状态进入 `blocked_by_environment` 或 `accumulating_with_failures`，取决于是否存在 completed samples。

## 9. 规模化路径

本阶段需要把后续规模化计划写入 spec/report，但不一次性实现重型调度。

建议 scale phases：

### Phase 1：启动积累

- 目标：100 requested samples。
- 形态：2 个默认任务 x 50 samples。
- 重点：验证 dataset index、failure boundary、accumulation report。
- 默认本阶段实现。

### Phase 2：分片扩大

- 目标：500 requested samples。
- 形态：5 个 batch shard x 100 samples，或 2 个任务 x 250 samples。
- 重点：引入 batch shard 编号、重复运行保护、已存在 batch result 复用。
- 下一阶段实现。

### Phase 3：规模化运行

- 目标：1000+ requested samples。
- 形态：多 batch、多任务、可能多 route 的离线运行。
- 重点：恢复、重跑、任务覆盖统计、环境健康检查、存储管理。
- 后续阶段实现。

本阶段只实现 Phase 1，并在 report 中输出 Phase 2/3 的建议和阻塞条件。

## 10. 测试策略

测试应覆盖结构和状态判断，而不是依赖真实 ManiSkill/SAPIEN 环境。

建议新增或扩展测试：

1. `SimulationAccumulationBatchSpec` 默认值测试。
2. 从 mixed `SimulationBatchResult` 生成 `SimulationDatasetIndex` 的测试。
3. 所有 requested samples 均 completed，且 failure boundaries 为空时，report 状态为 `ready_to_scale_with_conditions`。
4. completed 和 failed 并存时，report 状态为 `accumulating_with_failures`。
5. completed 为 0 且 failure boundary 包含 `environment_missing` 时，report 状态为 `blocked_by_environment`。
6. failure artifact 缺失但 sentinel 存在时，index 仍保留该失败样本。
7. CLI smoke test：在不依赖真实 ManiSkill/SAPIEN 的情况下可以生成 accumulation spec、dataset index 和 accumulation report。

默认验证仍为：

```bash
cd weld-experience-engine
uv run pytest -q
```

如本阶段修改 README 或 details，必须同步刷新对应 HTML 阅读版。

## 11. 实施边界

本阶段应做：

- 新增 accumulation 层数据结构。
- 新增从 batch result 到 dataset index 的汇总逻辑。
- 新增 accumulation report 状态判断。
- 扩展 batch pipeline 的样本数参数，保持默认行为不变。
- 新增 accumulation runner 和 CLI。
- 新增测试覆盖。
- 更新 README / details 中的下一阶段口径。

本阶段不做：

- 不做最终仿真器选型。
- 不做真实焊接质量验证。
- 不做真实机器人控制或 MoveIt 规划。
- 不做分布式队列、云端调度或并行执行平台。
- 不做复杂数据仓库、数据库或 UI。
- 不把工程师 Excel 参数表变成当前主流程的主数据源。

## 12. 验收标准

本阶段完成后，应满足：

1. 代码中存在可序列化的 accumulation spec、dataset index 和 accumulation report 结构。
2. 可以通过命令生成 100 requested samples 口径的 accumulation run 输出。
3. 输出中包含 `accumulation_spec.json`、`dataset_index.json`、`accumulation_report.json`。
4. 成功、失败、跳过样本都能进入 dataset index。
5. report 能区分 `accumulating_completed_samples`、`accumulating_with_failures`、`blocked_by_environment` 和 `ready_to_scale_with_conditions`。
6. 现有小批量默认入口命令仍保持兼容。
7. `uv run pytest -q` 通过。
8. README / details 的阶段口径从“先做数据积累前置报告”更新为“启动第一轮仿真数据积累，并建立后续规模化批次结构”。

## 13. 下一轮计划

本阶段之后，下一轮建议进入 **规模化仿真运行与条件性入口锁定**：

- 将一个 accumulation run 拆成多个 batch shard。
- 增加已存在 batch result 的复用和重跑策略。
- 统计任务覆盖、字段覆盖和 failure boundary 趋势。
- 判断 ManiSkill/SAPIEN 是否进入 `locked_for_next_batch_with_conditions`。
- 决定第三个 `WeldSkillUnit` 是否进入默认积累任务集合。

只有当 Phase 1 的 dataset index 和 accumulation report 稳定后，才应进入 500 或 1000+ 样本的规模化运行。
