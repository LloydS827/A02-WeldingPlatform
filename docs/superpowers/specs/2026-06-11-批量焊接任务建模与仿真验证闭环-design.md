# 批量焊接任务建模与仿真验证闭环设计

日期：2026-06-11

## 1. 背景

项目已经完成 `WeldSkillUnit -> SimulationTaskSpec -> ManiSkill/SAPIEN -> SimulationEvidenceBundle -> experience dataset -> accumulation report` 的前半段闭环，并完成 500 requested samples 与 1000 requested samples 的真实环境运行审查。

但当前批量能力主要证明的是“同一组默认任务可以按 shard 稳定运行、复用和汇总”。它还没有充分证明项目能批量生成具有焊接建模意义的任务变化，也还没有形成“建模变化是否值得进入仿真与专家审查”的最小验证层。

因此，下一阶段不应只继续扩大 sample 数量，也不应把跨批次 ledger 作为唯一主线。ledger 仍然需要，但它应服务于更核心的目标：建立批量焊接任务建模与仿真验证闭环。

## 2. 当前判断

当前节奏慢的根因不是测试数量不足，而是批量对象仍然偏“运行样本”，不是“建模样本”。

现有 pipeline 已经能回答：

- ManiSkill/SAPIEN route 能否运行。
- batch result、dataset index、accumulation report 能否生成。
- shard 是否能复用。
- completed sample 字段覆盖是否稳定。

现有 pipeline 还不能充分回答：

- 一个 `WeldSkillUnit` 能否批量展开成多组有语义差异的任务。
- 任务变化是否真实改变了几何、轨迹或姿态约束，而不是只改变 seed metadata。
- 哪些建模样本值得进入仿真运行。
- 哪些仿真完成样本值得进入专家审查。
- 当前 2 个默认任务族是否足以支撑下一批建模验证。

## 3. 目标

本轮目标是建立一个最小可用的批量建模验证层：

```text
BatchModelingSpec
-> ModeledSimulationTask
-> ModelingValidationReport
-> optional SimulationBatchSpec / ManiSkill run
-> expert-review candidate ids
```

完成后，项目应能够：

1. 从当前默认 `SimulationTaskSpec` 生成参数化 modeled task specs。
2. 每个 modeled task 明确记录来源任务、variation descriptor、建模假设和边界。
3. 生成 modeling validation report，统计任务覆盖、几何变化、路径长度范围、候选样本比例和阻塞原因。
4. 将通过建模验证的 task specs 作为后续仿真 batch 的输入。
5. 在 README / details 中把下一阶段主线从“继续扩大 requested samples”修正为“批量建模 + 小规模仿真验证 + 专家审查候选筛选”。

## 4. 非目标

本轮不做以下事情：

- 不宣称真实焊接质量验证完成。
- 不生成或替代 WPS/PQR。
- 不把 ManiSkill/SAPIEN 写成最终仿真软件选型。
- 不进入真实机器人执行。
- 不引入完整 Gazebo/MoveIt、Isaac、ROS 或真机控制集成。
- 不新增复杂高风险任务族作为默认主线。
- 不直接追求 5000 或 10000 requested samples。
- 不把参数变化写成真实工艺参数窗口；本轮只做 simulation modeling assumption。

## 5. 方案选项

### 方案 A：继续扩量运行

继续使用当前 2 个默认任务族，扩大到 5000 或 10000 requested samples。

优点：

- 工程风险低。
- 复用现有 accumulation pipeline。
- 容易得到更大的 completed 数字。

缺点：

- 主要验证运行稳定性，不能解决“批量建模不清楚”的问题。
- 样本价值会快速下降。
- 容易让项目继续停留在 pipeline proof，而不是 modeling proof。

不推荐作为本轮主线。

### 方案 B：直接新增多个任务族

新增 3-5 个 shipbuilding task family，并接入当前 batch / accumulation pipeline。

优点：

- 能快速扩大任务覆盖。
- 看起来更接近真实船舶焊接场景。

缺点：

- 缺少统一建模生成与验证层时，容易变成手写任务样例堆叠。
- 多任务族与参数化变化同时扩大，failure boundary 不容易归因。
- 容易过早进入复杂场景。

暂不推荐作为本轮主线。

### 方案 C：先建立批量建模生成与验证层

在现有 2 个默认任务族上，新增 deterministic modeling variation 层，生成小规模 modeled task specs 和 validation report。通过后再接入现有 batch / accumulation。

优点：

- 直接解决“批量对象不清楚”的核心问题。
- 保持任务复杂度受控。
- 能把建模变化、仿真运行、专家审查候选之间的边界说清楚。
- 为后续新增第三任务族和更大批次提供统一入口。

缺点：

- 第一轮 modeled task 仍是简化几何和姿态变化，不代表真实工艺参数窗口。
- 需要新增一个小的建模报告层。

推荐采用方案 C。

## 6. 设计

### 6.1 新增模块

新增 `weldcore.simulation_bakeoff.modeling`，负责建模层数据结构和纯函数。

建议新增对象：

- `BatchModelingSpec`
- `TaskModelingVariation`
- `ModeledSimulationTask`
- `ModelingCoverageSummary`
- `ModelingValidationIssue`
- `ModelingValidationReport`

这些对象只表达建模层事实，不直接运行仿真，也不直接写真实质量结论。

`ModeledSimulationTask` 必须包含 `task_spec: SimulationTaskSpec`，并额外携带来源任务、variation、assumption 和 evidence metadata。`modeled_task_specs.json` 输出的是可重建为 `tuple[SimulationTaskSpec, ...]` 的任务列表，而不是只供阅读的 wrapper 报告；如果需要保留 wrapper 信息，应写入 `modeled_tasks.json` 或 report，而不能让 `modeled_task_specs.json` 失去 batch spec 可消费性。

### 6.2 建模 variation

第一轮采用 deterministic lightweight policy，例如：

- `path_length_scale`
- `lateral_offset_m`
- `vertical_offset_m`
- `orientation_rz_delta_deg`
- `geometry_profile`

这些 variation 必须实际作用到 `SimulationTaskSpec.seam_path`，不能只记录在 metadata。

每个 variation 都必须记录：

- `source_task_id`
- `modeled_task_id`
- `variation_index`
- `variation_descriptor`
- `assumption_notes`
- `evidence_notes`

默认每个当前 task spec 生成 4 个 modeled tasks。当前 2 个默认任务族会得到 8 个 modeled task specs。这个规模足以验证建模闭环，同时不会扩大到不可控。

### 6.3 建模验证

`ModelingValidationReport` 应至少包含：

- `modeling_batch_id`
- `status`
- `source_task_count`
- `modeled_task_count`
- `valid_modeled_task_count`
- `expert_review_candidate_count`
- `source_task_ids`
- `modeled_task_ids`
- `expert_review_candidate_task_ids`
- `coverage_summary`
- `issues`
- `known_limitations`
- `next_step_recommendation`

建议 status：

- `ready_for_simulation_batch`
- `blocked_by_modeling_issue`
- `ready_for_expert_review_candidates`

本轮只要建模任务全通过基础验证，即可返回 `ready_for_simulation_batch`。专家审查候选可以作为 report 中的 candidate ids，不直接触发专家审查系统。

第一轮 expert-review candidate 规则保持确定性：所有通过建模验证、且相对 source task 发生实际 path 几何变化的 modeled tasks 都进入 `expert_review_candidate_task_ids`。如果某个 modeled task 未发生几何变化、缺少必须输出、丢失边界声明或触发 forbidden term，则不进入候选，并在 `issues` 中记录原因。

### 6.4 建模验证规则

第一轮规则保持简单：

- modeled task id 必须唯一。
- seam path 至少 5 个点。
- path length 必须大于 0。
- modeled task 必须保留 `tcp_trajectory`、`tool_orientation`、`task_status` expected outputs。
- modeled task 必须保留 `path_continuity` evaluation metric。
- modeled task 必须保留 `real_welding_quality` 和 `WPS/PQR` out-of-scope 边界。
- variation 必须造成 path 几何变化，不能只改变 metadata。
- report 中不得出现熔池、热过程、冶金等当前禁用主线。

### 6.5 CLI / report

新增轻量 CLI：

```bash
uv run python -m weldcore.simulation_bakeoff.modeling_pipeline \
  --outdir artifacts/simulation/modeling-validation \
  --modeling-batch-id default-batch-modeling-v1 \
  --variants-per-task 4
```

输出：

- `modeling_spec.json`
- `modeled_task_specs.json`
- `modeling_validation_report.json`

CLI 不默认运行 ManiSkill/SAPIEN。它只证明批量建模对象可以生成并被验证。后续可将通过验证的 modeled task specs 接入 batch / accumulation pipeline。

### 6.6 与现有 pipeline 的关系

本轮不改动 100/500/1000 accumulation 的默认行为。

新增建模层应保持向后兼容：

- `default_simulation_task_specs()` 不变。
- `default_maniskill_batch_spec()` 不变。
- `run_maniskill_accumulation_pipeline()` 不变。
- `run_maniskill_batch_pipeline()` 默认行为不变，本轮不要求它新增 `task_specs` CLI 输入。

建模层作为前置入口：

```text
default_simulation_task_specs()
-> default_batch_modeling_spec()
-> build_modeled_simulation_tasks()
-> build_modeling_validation_report()
-> later: default_maniskill_batch_spec(task_specs=modeled_task_specs)
```

本轮必须验证 batch spec 层兼容：`modeled_task_specs` 可传入 `default_maniskill_batch_spec(task_specs=...)`，并能生成 expected requested sample count 与 modeled task ids。这个验证证明建模输出不是孤立报告层；但本轮不默认运行 ManiSkill/SAPIEN，也不修改 accumulation pipeline 默认入口。

### 6.7 文档更新

更新：

- `README.md`
- `README.html`
- `details.md`
- `details.html`

文档应明确：

- 当前项目已经完成 1000 requested samples 运行审查。
- 下一阶段主线调整为“批量焊接任务建模与仿真验证闭环”。
- accumulation ledger 是 supporting layer，不再是唯一主线。
- 新 CLI 用于生成 modeled task specs 和 modeling validation report。
- 本轮仍不代表真实焊接质量、WPS/PQR、最终仿真器选型或真实机器人执行。

## 7. 成功标准

本轮完成后必须满足：

1. 新增建模层数据结构和纯函数。
2. 默认 2 个任务族 x 4 variations = 8 modeled task specs。
3. modeled task specs 的 seam path 确实发生几何变化。
4. validation report 输出 `ready_for_simulation_batch`。
5. report 能列出 expert-review candidate task ids。
6. 新 CLI 能写出 3 个 JSON artifact。
7. 建模输出可传入 `default_maniskill_batch_spec(task_specs=...)`，生成的 requested sample count 与 task ids 正确。
8. 单元测试覆盖建模生成、验证报告、batch spec 兼容和 CLI artifact。
9. README / details / HTML 同步更新。
10. 默认测试套件通过。

## 8. 风险与控制

### 风险：把建模 variation 写成真实工艺参数

控制：variation 字段和文档都使用 `simulation_modeling_assumption`、`not_real_welding_process_parameter` 等边界语义。

### 风险：第一轮 modeled task 仍过于简单

控制：承认第一轮只做几何/姿态/路径级变化；下一轮再引入 task family generator 或第三任务族。

### 风险：与现有 accumulation pipeline 耦合过深

控制：本轮不改默认 accumulation 行为，只新增可消费的 modeled task specs。

### 风险：继续停留在报告层

控制：下一轮必须把通过验证的 modeled task specs 接入小规模 ManiSkill batch，并从 completed samples 中筛 expert-review candidates。

## 9. 下一阶段建议

本轮完成后，下一阶段应执行小规模仿真验证：

```text
8 modeled task specs
-> 2-5 samples per modeled task
-> 16-40 requested samples
-> batch result + modeling validation cross-reference
-> expert-review candidate set
```

如果该闭环稳定，再考虑：

1. 新增第三个默认任务族。
2. 建立跨批次 modeling ledger。
3. 扩展到 100+ modeled task specs。
4. 将 expert-review candidate 与 `RobotProcessPackageDraft` 更紧密绑定。
